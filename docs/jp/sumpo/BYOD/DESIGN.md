## デモの対象業態

デモ企業を、**地域の設備工事・保守会社「あおば設備サービス株式会社」（架空）**に固定する

- 空調・電気・消防設備の工事、定期保守、緊急修理を行う
- 社員11名と協力会社8名の計19名で、事務所1拠点と複数の現場を動かす
- 代表・工事責任者1名、総務・安全管理2名、営業・現場監督3名、自社技術者5名、協力会社8名で構成する
- 安全連絡、工程変更、停電作業の可否確認、現場作業、入退場を本デモの中心業務にする
- 見積、受注、請求、保守契約台帳は次段階とし、まず「必要な情報だけを確実に届ける」に絞る

設備工事・保守は、現場ごとに参加者が変わり、社員と協力会社が同じ仕事をしながら見せる情報を分ける必要がある。BYOD、指名回答、最小権限、QR打刻の価値を一つの物語で示しやすい

基盤は汎用のまま保ち、デモの会社名、役割名、連絡、作業だけを具体化する。産業機械保守や葬祭業へ展開するときは、ロールキーと権限モデルを変えず表示名とデモデータを差し替える

## 0. 確定した前提

| 項目 | 決定 | 理由 |
|---|---|---|
| 対応端末の下限 | **iOS 16+ Safari / Android 9+ Chrome** | パスキー必須で割り切る。Android は Chrome を指定（→ 3章） |
| 実行基盤 | **Cloudflare Workers（無料枠）** | OS更新・TLS更新・Docker が全て不要。保守がほぼゼロ |
| 実装言語 | **TypeScript（Hono + JSX SSR）** | Workers 上で Go は実用的に動かないため |
| フロント | **HTMX**（ビルド工程なし） | 古い端末で確実に動き、端末に状態を残さない |
| DB | **D1**（SQLite 互換） | 分離のデモが D1 でしか成立しない。実運用では Neon を検討（→ 12.1.1） |
| 添付保存 | **D1 の BLOB（1枚1MB上限）** | R2 を使わず無料枠を確実に維持（→ 2.4） |
| サンプル機能 | **営業 / 現場 / れんらく / やること / 出退勤(QR)** | 請求・入金・精算は Phase 6 以降に保留 |

**月額 0 円で全て収まる（無料枠内）。** サーバを1台も持たないこと自体が、BYOD＝「持たない経営」の訴求と同じ方向を向く。独自ドメインを使う場合のみ、ドメイン代（年1,500円程度）が別途かかる。

保留した機能（データモデルは拡張余地を残す）:
- 営業〜見積〜受注〜計画〜実施〜請求〜入金
- 立替金・出張旅費精算（カメラ連携＝専用アプリの必要性を示す題材）

### 0.1 なぜ VPS + Go をやめたか

当初は「東京VPS + Docker Compose + Go」で設計したが、以下の理由で切り替えた。

- **保守がゼロになる** — OS のセキュリティ更新、TLS 証明書更新、Docker イメージ更新が全て消える
- **分離のデモが強くなる**（後述）— 設定ファイル1枚で説明が終わる
- **移行コストが今なら実質ゼロ** — 書いたのが設計書だけで、コードが1行もない段階だった

代償は「データ所在地を日本国内と保証できない」ことだが、**デモは架空データのみを扱うため問題にならない**。実導入時には論点として復活する（→ 12章）。

## 1. 想定ユーザーとロール

19 名想定。**協力会社の権限が最小**であることが、BYOD セキュリティのデモとして最も重要。

| ロール | 人数 | れんらく | やること | 出退勤 | 管理機能 |
|---|---|---|---|---|---|
| 代表・工事責任者 | 1 | 全社発信・全閲覧 | 全件閲覧 | 全員閲覧・承認 | 監査ログ閲覧 |
| 総務・安全管理 | 2 | 全社発信・全閲覧 | 全件作成・割当 | 打刻修正・承認・CSV | ユーザーの稼働/停止・強制ログアウト |
| 営業・現場監督 | 3 | 管理者を含む3名以上へ発信 | 全現場を閲覧・作成・割当 | 自分の打刻 | なし |
| 自社技術者 | 5 | 管理者を含む3名以上へ発信・回答 | 全現場を閲覧・担当現場で作成・自分の担当を更新 | 自分の打刻 | なし |
| 協力会社員 | 8 | 参加スレッドだけ閲覧・回答 | 担当現場を閲覧・自分の担当を更新 | 自分の打刻（現場限定） | なし |
| **打刻端末** | 1〜 | なし | なし | **QR検証と打刻記録のみ** | なし |

デモ時にロールを切り替えて同じ画面を並べるのが、最も説得力のある見せ方になる。

**端末数の制限は設けない。** 認証するのは人であって端末ではないため（→ 3章）。

### 1.1 名前切り替えは打刻の生体認証を免除する

デモの名前切り替え（`/demo/switch`）はパスキーを経ないので、作られる
セッションは `credential_id` が null になる。そのままだと
**切り替えるたびにその日1件目の打刻で生体認証**が挟まり（→ 3章の
ステップアップ認証）、商談の実演が止まる。

`needsStepUp` 自体は緩めない。「パスキーを経ていないセッションは不可」は
本番の安全性そのもので、ここを崩すと打刻の意味が消える。代わりに
**切り替えで作ったセッションにだけ印を付け**（`sessions.via_demo_switch`）、
打刻の判定でその印を見て免除する。

| セッション | 資格情報 | その日1件目の打刻 |
|---|---|---|
| 通常のログイン（パスキー） | あり | 認証済みなので通る |
| 通常のログイン（認証が古い） | あり | **生体認証を求める** |
| **名前切り替え** | なし | **免除**（印があるため） |
| 資格情報なし・切り替えでない | なし | **生体認証を求める** |

最終行が重要で、**印が無いセッションの扱いは一切変わらない**。免除は
デモ経路だけに閉じている。実導入で `/demo/*` を落とせば、印の付いた
セッションは生まれない。

### 1.2 打刻端末は「仮想ユーザ」として認証する

会社に設置する読み取り端末は、**人間と同じくパスキーで認証されたアカウント**として扱う。`terminal` ロールを持つ仮想ユーザで、設置時に管理者が一度だけ登録する。

これにより、認証を持たない端末が打刻 API を叩けなくなる。**未登録の端末から QR を読み取られても、POST が認証で弾かれる。**

- 権限は極端に狭い。**QR 検証と打刻記録だけ**で、れんらくもやることも案件情報も一切見えない
- 稼働/停止の仕組み（→ 3章）がそのまま使える。**端末を撤去したら「停止」にすれば即座に無効化できる**
- 打刻レコードの `terminal_id` が「どの端末で打刻されたか」の裏付けになる
- 招待・パスキー登録のフローは人間とまったく同じものを使う

**セッションの寿命だけ人間と分ける。** 固定端末が8時間で切れると現場が止まるため、`terminal` ロールに限りアイドルタイムアウトを適用しない（絶対期限のみ、30日）。設置場所が物理的に固定されており、かつ画面に業務データを一切表示しないことが、これを許容する根拠になる。

## 2. 実行基盤の構成

```
                     インターネット
                          │  Cloudflare エッジ（WAF / DDoS / TLS 自動）
                     ┌────▼──────┐
                     │  byod-ssr  │  公開ルートを持つ唯一の Worker
                     │  (Worker)  │  HTMLを組んで返すだけ
                     └────┬──────┘
            service binding│  ← 内部呼び出し。インターネット経由しない
                     ┌────▼──────┐
                     │  byod-api  │  ルート未設定＝外部から到達不能
                     │  (Worker)  │  認可判定はすべてここ
                     └─────┬──────┘
                           │
                       ┌───▼───┐
                       │  D1   │  本文・添付BLOB・監査ログ
                       └───────┘
```

### 2.1 分離の担保 — これがデモの目玉

**SSR Worker には D1 のバインディングを書かない。** バインディングが無いということは、そのハンドルがコード内に存在しないということ。ルーティングで到達を禁じるのではなく、**参照する手段そのものが無い**。

```jsonc
// ssr/wrangler.jsonc — DBが「無い」
{
  "name": "byod-ssr",
  "routes": [{ "pattern": "byod.sumpo.uk", "custom_domain": true }],
  "services": [{ "binding": "API", "service": "byod-api" }],
  "assets": { "directory": "./public" }
}

// api/wrangler.jsonc — ここだけがデータを持つ。routes が無い＝外部から叩けない
{
  "name": "byod-api",
  "d1_databases": [{ "binding": "DB", "database_name": "byod" }]
}
```

service bindings は**無料枠で利用できる**（公式ドキュメントの「Workers Standard pricing のみ」という記述は、有料/無料の区別ではなく、廃止された Bundled / Unbound 課金モデルに対する現行モデルを指す）。

商談ではこの2ファイルを並べて見せる。`docker network inspect` の出力より、非技術者に圧倒的に伝わる。

### 2.2 アカウントとドメインは既存資産から分離する

**BYOD 専用の Cloudflare アカウントを新規に作り、専用ドメイン `sumpo.uk` を使う。** 既存の `azukid.com` / `azuki-api` とは同居させない。ドメインは取得済み。

当初は `byod.azukid.com` を検討したが、**同一アカウントに置くと課金枠以外の問題が生じる**ため見送った。

| 論点 | 同居した場合の問題 |
|---|---|
| **API トークン**（決め手） | Cloudflare の API トークンは**アカウント単位**でスコープされ、**Worker 単位に絞れない**。BYOD のデプロイ鍵が漏れれば `azuki-api` も書き換えられ、D1 も読める |
| 事故の波及 | 無料枠を使い切ると**アカウント内の Worker が全部止まる**。デモ側のポーリングのバグで本番 API が道連れになる |
| 監査ログ | Cloudflare のアカウント監査ログが1本に混ざり、追跡しづらい |
| WAF ルール数 | 無料プランは Zone 単位でカスタムルール数に上限がある。認証エンドポイントを持つ BYOD 用のレート制限が既存サイトの枠を食う |
| 将来の譲渡 | 実運用で顧客へ引き渡す際、**アカウントごと渡せる形**でないと移設作業が発生する |

決め手は API トークンの粒度。本設計は「SSR は D1 に到達できない」まで分離を徹底しているのに、**デプロイ鍵が本番 API と共通**では筋が通らない。年1,500円程度のドメイン代で、鍵の分離・事故の切り離し・譲渡可能性がまとめて手に入る。

#### 2.2.1 ホスト名と RP ID

**アプリの URL は `https://byod.sumpo.uk`、WebAuthn の RP ID は `byod.sumpo.uk`。**

ルート（`sumpo.uk`）を直接使わずサブドメインを切るのは、**RP ID を BYOD に閉じる**ため。RP ID をルートにすると、将来 `sumpo.uk` を別用途（他のサンプル、ポートフォリオ等）に使う際にパスキーのスコープを共有してしまう。サブドメインにしておけば、`demo2.sumpo.uk` のような別サイトを立てても認証は混ざらない。

- `uk` は Public Suffix List 上の公開接尾辞であり、`sumpo.uk` は通常の登録可能ドメイン。**`__Host-` Cookie も RP ID も問題なく機能する**（`*.workers.dev` を使う場合に生じる懸念は該当しない）
- `azukid.com` 配下にしないのは、紹介サイトと WebAuthn のスコープを共有しないため

#### 2.2.2 「後からドメインを移す」は選べない

「まず `azukid.com` に置き、規模が大きくなったら専用ドメインへ移す」という進め方は、**この設計では成立しない**。

**WebAuthn の RP ID は登録時に固定され、後から変更できない。** ドメインを移すと**全ユーザーのパスキーが無効になり**、招待コードからの再登録が必要になる。招待は対面で渡す設計（→ 3章）なので、50人なら50回の対面作業になる。データ移行ではなく**全社員を集め直す運用イベント**であり、**利用者が増えたあとほど移行コストが跳ね上がる**。

しかも負荷は移行理由にならない。11.1.4 のとおり50人規模でも無料枠の日次上限に届かず、超えても有料プラン（$5/月）に上げるだけで構成もコードも変わらない。「規模が大きくなったら」という条件は**発火しない**。

したがって**最初から専用ドメインで始める**。デモ段階で実ユーザーがいないうちに確定させておく。

#### 2.2.3 アカウントの構成と作成手順

| | メール | 保有するもの |
|---|---|---|
| 既存アカウント | `git@art.jp` | `azukid.com` / `azuki-api` |
| **BYOD アカウント** | **`masa@art.jp`** | **`sumpo.uk`** / `byod-ssr` / `byod-api` / D1 |

**Cloudflare は1メールにつき1アカウント。** `+` を使ったサブアドレス（`git+byod@art.jp`）やドットを挿入した変種は**ベースアドレスと同一と判定されて弾かれる**ため使えない。`masa@art.jp` はローカル部が異なる別アドレスなので問題ない（**要件は、そのアドレスで確認メールを受信できること**）。

手順は次のとおり。**招待は新アカウント側から出す**ので、順番を逆にはできない。

1. ~~**`masa@art.jp` で新規アカウントを作成**~~ — **完了**
2. ~~**`sumpo.uk` を Zone として追加**~~ — **完了**。`masa@art.jp` のアカウントで取得・登録済みで、ネームサーバは Cloudflare（`aria` / `ace.ns.cloudflare.com`）を向いている。**Zone は別アカウントへ移動できない**ため、最初から正しいアカウントで取得できているのは重要
3. **`git@art.jp` を Member として招待** — `masa@art.jp` でログインしたまま実行
   - ダッシュボードの **Members** → **Invite**
   - Invite members: `git@art.jp`
   - Roles: **Administrator**（**Super Administrator は選ばない**）
   - **Continue to summary** → **Invite**
4. **`git@art.jp` 側で招待メールを承諾** — 「Skip email confirmation」は Enterprise 限定のため、無料プランではメール承諾が必須
5. 以降、`git@art.jp` のログイン1つでダッシュボードのアカウント切り替えができる

**役割を Administrator に絞ることが分離の要。**

| 役割 | できること | 採否 |
|---|---|---|
| Super Administrator | 全権限。**アカウント所有 API トークンの作成**・メンバー管理・請求 | **不可**。実質同じ鍵になり、アカウントを分けた意味が消える |
| **Administrator** | アカウント全体の編集。**トークン作成・メンバー管理・請求は不可** | **これを使う** |
| Workers Platform Admin | Workers / D1 / KV / R2 のみ | さらに絞りたい場合の選択肢 |

2.2 で問題にしたのは「BYOD のデプロイ鍵が漏れると `azuki-api` も書き換えられる」ことだった。Administrator は**アカウント所有トークンを作成できない**ので、この経路が塞がれる。**請求と無料枠もアカウント単位で分離されたまま**になる。

役割の変更は Members → 対象を選び **Edit** → **Continue to summary** → **Update**。剥奪は **Revoke**。

#### 2.2.4 デプロイ時の認証

日常のデプロイは `wrangler` から行うため、ダッシュボードを開く頻度は低い。BYOD 用のトークンは**新アカウントで発行し、環境変数で渡す**。これにより招待の有無に関わらず鍵が分離される。

```
CLOUDFLARE_API_TOKEN=<BYODアカウントで発行したトークン> wrangler deploy
```

> **未確認**: 無料プランの WAF ルール数上限、およびアカウント切り替え UI の詳細（コミュニティ情報からの推定を含む。アカウント作成時に確認すること）。

### 2.3 SSR ↔ API 間の信頼関係

**SSR は自分でユーザーの身元を判定しない。** ブラウザから受け取った不透明なセッション Cookie の値を、そのまま API に転送するだけ。

```
ブラウザ ──[__Host-sid=<不透明な32バイト>]──▶ SSR ──[そのまま転送]──▶ API
                                                                      │
                                          セッション解決・ロール判定・認可 ◀┘
                                                                      │
SSR は「描画に必要なデータ」だけを受け取る ◀───────────────────────────┘
```

この形の利点は、**SSR が権限を詐称できない**こと。SSR がロールを主張する JWT を発行する方式だと、SSR の侵害＝権限昇格になる。セッション ID を解決できるのは D1 を持つ API だけなので、SSR に RCE が通っても「他人のセッション ID を知る」以上のことができない。

API 側のレート制限（アクター単位）と、Cloudflare WAF のレート制限（IP 単位）を二層で敷く。

### 2.4 無料枠で収めるための制約と対策

無料枠の主な上限と、本設計での扱い。

| 上限 | 値 | 本設計での扱い |
|---|---|---|
| リクエスト | 100,000 / 日 | QR 画面のポーリングが唯一の risk（下記） |
| CPU 時間 | **10ms / 呼び出し** | 実質の制約。ただし I/O 待ちは計上されない |
| サブリクエスト | 50 / リクエスト | 1画面あたり 1〜3 回。余裕 |
| Worker サイズ | 3MB（gzip後） | HTMX + 手書きCSS のみ。桁違いに余裕 |
| D1 | 5GB / 読 500万行・書 10万行 per 日 | 19名なら誤差。ただし QR の書込に注意（下記） |

**CPU 10ms は思ったより余裕がある。** D1 クエリや service binding 呼び出しの待ち時間は CPU 時間に計上されない。加えて **2 Worker に分けたことで、SSR と API がそれぞれ独立に 10ms を持つ**。ECDSA P-256 の署名検証は 1ms 未満、JSX の SSR も数 ms で収まる。

対策が要るのは 2 点だけ。

1. **一覧画面は必ずページネーションする** — 監査ログのような大量行を一度に JSX でレンダリングすると 10ms を超えうる。1ページ 50 件を上限にする
2. **QR 画面のポーリングを抑える** — 6.3 で対応

**静的アセットは no-store の対象外にする。** `htmx.min.js` / `app.css` は機密ではないので、ファイル名にハッシュを付けて `Cache-Control: public, max-age=31536000, immutable` を返す。端末に残してよいのは**機密情報でないファイルだけ**、という線引きを明確にする（4章）。これでリクエスト数も減る。

**R2 は使わない。** R2 自体に無料枠（10GB）はあるが、有効化の条件を確実に把握できていないため、無料枠内で完結させる目的では避ける。添付は D1 の BLOB に 1枚 1MB 上限で保存する。デモの画像枚数なら 5GB 枠に対して問題にならない。実導入時に R2 へ移す。

## 3. 認証設計 — パスキー

ライブラリ: `@simplewebauthn/server`（Web Crypto ベースで Workers 上で動作）

### 3.1 登録フロー

**招待コードは対面でのみ渡す。** 出社時に本人を総務・安全管理の前に呼び、**総務・安全管理の端末に表示されたコードを本人が自分の端末に入力する**。

```
出社時、総務・安全管理の前で:
  総務・安全管理が招待を発行 → 自分の端末画面に QR とコードを表示（有効期限 10分）
       └→ 本人が標準のカメラアプリで QR を読み取る（URLにコードが載っている）
       │    └→ 読めない端末なら、コードを手入力して同じ画面へ
            └→ 管理者が招待時に名前とロールを設定
                 └→ WebAuthn 登録（userVerification: required）
                      └→ credential（+ AAGUID・登録日時）を D1 に保存
                           └→ 管理画面に「パスキー登録」を通知
```

#### 3.1.1 QR とコードを併記する（実装時の決定）

**QR を主、コードを従とし、必ず同じ画面に両方出す。**

QR にすると、**URL を伝える手間ごと無くなる**のが大きい。
コードだけの方式では「`byod.sumpo.uk` を開いて、登録画面に行って、
このコードを入れて」と3つ伝える必要があり、URL の打ち間違いも起きる。
QR なら読み取って登録画面が開くまでが1手になる。

**カメラ権限は要らない。** スマホの標準カメラアプリが QR を認識して
ブラウザを開くだけなので、`getUserMedia` も `BarcodeDetector` も使わない。
打刻（→ 6.3）で BYOD 側にカメラを使わせない判断とは矛盾しない
（あちらは毎日全員、こちらは入社時に1回だけ、かつ Web の権限が不要）。

**コードを残すのは、読めない場面が必ずあるため。**
古い Android・カメラの故障・管理された端末・枠に収められない人。
対面の場で詰まると気まずいので、代替を同じ画面に並べておく。

コードが URL に載ることについて:

- 対面で画面に表示するだけで、**SMS もメールも紙も経由しない**前提は変わらない
- `Referrer-Policy: no-referrer` により外部サイトへ漏れない
- `Cache-Control: no-store` によりキャッシュにも残らない
- 端末の履歴には残るため、**読み込み直後に `history.replaceState` で
  `?c=` を URL から消す**（→ public/webauthn.js）

#### 3.1.2 QR は SSR で SVG を組み立てる

外部ライブラリを使わない。CSP が `default-src 'none'` なので CDN からは読めず、
npm 依存を足すとバンドルも重くなる。`ssr/src/views/qr.ts` に
**バイトモード・誤り訂正レベル M・版2〜6** だけの実装を置く。

画像リクエストも client JS も発生せず、SSR が返す HTML に SVG が入るだけ。

> **実装時の教訓**: 最初の実装は**全く読み取れない QR** を出していた。
> 見た目はそれらしいので、目視では気づけない。
> 原因は関数パターンの2箇所で、**形式情報の予約をタイミングパターンより
> 後に行ったために `(6,8)` が潰れていた**こと、および形式情報の配置ミス。
> **独立したデコーダ（jsQR）で読み直す検証を必ず行うこと。**
> 版7以降はブロック分割の規則が変わるため、検証できていない版は
> 意図的に対象外にしてある（招待URLは40バイト前後で版3に収まる）。

SMS もメールも紙も使わない。**コードが通信経路にも紙にも一切残らない**のが利点で、漏洩経路そのものを無くせる。有効期限を 10 分と短くできるのも対面だからこそ。

- 本人確認は「総務・安全管理が本人の顔を見ている」ことで担保される。BYOD の初回登録としてはこれが最も確実
- 総当たり対策は Turnstile ＋ 試行回数制限。ただし 10 分・対面という条件下では現実的な脅威ではない
- **50人規模でも、入社時に1人1回だけの作業**なので運用負荷は問題にならない

招待コード方式にするのは、**パスワードを一度も発行しない**ため。パスワード運用が存在しないこと自体が営業トークになる。

#### 3.1.3 入力の揺れは全部こちらで吸収する（実装時の決定）

**読み上げた人と入力する人が別**なので、入力は必ず揺れる。
「入力し直してください」と言わせないために、照合前に正規化する。

| 入力 | 例 | 通る |
|---|---|---|
| 小文字 | `3jhu-lqgy` | ○ |
| ハイフン無し | `3JHULQGY` | ○ |
| 空白区切り | `3JHU LQGY` | ○ |
| ダッシュ類 | `3JHU—LQGY` | ○ |
| 全角 | `３ＪＨＵ－ＬＱＧＹ` | ○ |
| 前後の空白 | `  3jhu-lqgy  ` | ○ |

**区切りの位置には意味を持たせない。** `3JH-ULQGY` のように
ハイフンがずれていても通る。区切りは読みやすさのためだけにあり、
位置を検証しても利用者が困るだけで、セキュリティ上の利得は無い。

`ALPHABET` から紛らわしい文字（`0/O` `1/I`）を除いてあるため、
大小と区切りを潰しても衝突しない。**除外していなければこの正規化は成立しない**。

- iOS がハイフンを em ダッシュに自動変換しても弾かれない
- 入力欄は `autocorrect=off` / `spellcheck=false`。コードを英単語に直させない
- 記号だけの入力（`----`）は **DB を引く前に** 弾く。
  総当たり対策のカウンタ（→ `recordFailedAttempt`）を無駄に消耗させないため

### 3.2 表示名は管理者が決める「名前」へ統一

管理者が招待時に**名前を設定**し、アプリ内の表示はすべてこれを使う。本人は登録時にも登録後にも名前を変更できず、管理者だけが管理画面から変更できる。

- れんらくの発信者名、既読一覧、やることの担当者、打刻端末の表示（→ 6.3）まで一貫して同じ名前
- 大文字小文字・全角半角・カナひらがな・空白を正規化し、既存名との編集距離が2以上の場合だけ招待・変更できる
- 名前の変更は日時・変更者とともに監査ログへ記録する
- 既存利用者の表示名は移行時に `users.name` へ引き継ぎ、表示を変えない
- 名前と稼働状態の変更は**名簿のポップアップ**で行う（→ 6.3）。管理画面に利用者管理の別枠は持たない
- 協力会社の所属は協力会社マスタ（→ 6.3.1）から選ぶ
- 協力会社の人は、名前一覧で `記号＋名前`（スペースなし）と表示して所属を判別できるようにする

### 3.3 2つ目以降のパスキー

多くの利用者にとっては不要。iPhone と iPad、あるいは Android と Windows PC の Chrome なら、**パスキーは同期されるので何もしなくても使える**。

必要になるのは iPhone と Windows PC のようにエコシステムをまたぐ場合だけで、その場合も 2 通りで済む。

- **クロスデバイス認証で入る** — PC に出た QR をスマホで読む。PC 側に何も登録しない
- **その端末にパスキーを追加する** — 上記でログインしたあと「この端末にパスキーを登録」を押すだけ

追加用のトークンや QR を発行する専用フローは持たない。**すでに認証済みのセッション上で WebAuthn 登録を1回走らせるだけ**で足りる（`excludeCredentials` で重複登録を防ぐ）。登録数の上限も設けない。

### 3.4 ログイン

- Discoverable credential（usernameless）。ユーザーは ID を入力しない
- `userVerification: "required"` — 生体 or 端末 PIN を毎回必須
- `signCount` を検証し、巻き戻りを**クローン疑い**として検出・ブロック

### 3.5 1人が複数デバイスを使う前提に立つ

**代表・管理・営業は PC とスマホを併用する。これが通常であって例外ではない。** 設計はこれを前提に組む。

```
users (1) ─── (N) credentials   パスキー（＝資格情報）
      (1) ─── (N) sessions      同時に複数存在してよい。上限なし
```

端末という単位のテーブルは持たない（→「認証の対象は『人』」）。

### 3.6 「デバイス毎のパスキー」は Apple でも Android でも成立しない

要件の「認証はデバイス毎のパスキー」は、技術的に達成できない。ここは正確に理解しておく必要がある。

**Apple の場合**

- iPhone と iPad が同じ Apple ID なら、パスキーは iCloud キーチェーンで同期され、**同一の credential ID を提示する**。サーバから見て2台は区別できない
- iOS の platform authenticator は常に同期パスキー（`BE=1`）で、端末固定（`BE=0`）を選ばせる手段がない

**Android の場合 — Apple より同期範囲が広い**

- Google パスワードマネージャー（GPM）のパスキーは、**Chrome on Windows / macOS / iOS / iPadOS / Android を横断して同期する**。iCloud キーチェーンが Apple 製品内に閉じるのに対し、GPM は **OS をまたいで**同期する
- つまり Android スマホで登録したパスキーが、そのまま本人の Windows PC の Chrome でも使える。「デバイス毎」からはさらに遠い
- Android 14+ では 1Password などサードパーティをパスキープロバイダに選べる（OEM によっては設定が反映されない機種がある）

`BE=0` を強制すれば端末固定にできるが、そうすると **iOS も Android も platform authenticator が全滅し、物理セキュリティキーしか使えなくなる**。BYOD の前提が崩れるので選択肢にならない。

したがって **「credential = デバイス」という前提を捨てる**。credential は「その人が持つ資格情報の1つ」に過ぎない。端末は識別の対象にせず、**記録の一項目として残すだけ**にする（次項）。

### 3.7 クロスデバイス認証（hybrid）

スマホのパスキーで、**PC 側のログインを承認できる**（PC に QR が出て、スマホで読む）。Chrome は全プラットフォームで対応している。

これは「認証するのは人であって端末ではない」という設計と噛み合う。PC 側にパスキーを登録しなくても、PC には通常どおりセッションが立ち、ログには「Chrome / Windows から」と残る。特別な扱いは何も要らない。

BYOD としても実用的で、「事務所の PC にわざわざ登録しなくても、自分のスマホで入れます」という説明ができる。

### 3.8 パスキープロバイダの表示（AAGUID）

パスキー一覧と監査ログに「Google パスワードマネージャー」「iCloud キーチェーン」「1Password」「Windows Hello」といった**プロバイダ名を表示**する。コミュニティ管理の AAGUID リスト（`passkeydeveloper/passkey-authenticator-aaguids`）を同梱すれば実装できる。

端末を管理しない代わりに、**ログの可読性はここで確保する**。「iCloud キーチェーンの資格情報で、iPhone の Safari から、渋谷区の IP で」まで読めれば、事後の追跡には十分足りる。

> **実装上の必須要件**: AAGUID は**登録時のレスポンスにしか含まれず、認証時のアサーションには含まれない。** 登録時に必ず `credentials.aaguid` へ保存すること。取り漏らすと、後から埋める手段は**再登録しかない**。

### 3.9 Android 特有の運用上の注意

技術以前に、現場で詰まるのはここ。

- **ブラウザは Chrome を指定する** — Google が公式に対応を明記しているのは Chrome のみ。Samsung 端末は Samsung Internet が既定ブラウザのことがある（Chromium ベースなので動作する可能性は高いが保証外）。要件の「スマホ標準ブラウザで利用」は、**Android では「Chrome を使う」と読み替える**必要がある
- **画面ロックの設定が事実上の前提** — `userVerification: "required"` を使う以上、画面ロック（または GPM の PIN）が設定されていない端末ではパスキーを作れない。**私物端末に画面ロックをかけていない従業員は実在する**ので、導入時の案内に必ず含める
- **Android 9 以上**（API 28+）。これより古い端末は対象外

### 3.10 認証の対象は「人」。端末は識別しない

**パスキーが担保するのは個人の認証であり、そこまでで十分とする。** 端末を能動的に識別・管理する仕組みは持たない。

一度は「永続 Cookie で端末に ID を振り、台帳を作って登録台数を制限する」設計にしたが、破棄した。理由:

- パスキーが同期される以上、**端末という単位はもともとサーバから見えない**
- Cookie で振った ID は **Cookie を消すだけで別端末になる**。上限管理としての実効性がない
- 「端末に何も残さない」という中心的な要件に対して、**永続 Cookie を1つ増やす**のは筋が悪い

結果として、**端末に置かれる Cookie はセッション Cookie ただ1つ**になり、それもブラウザを閉じれば消える。営業上もこのほうが説明が短い。

| Cookie | 寿命 | 役割 |
|---|---|---|
| `__Host-sid` | ブラウザ終了／アイドル15分 | 認証。**これだけ** |

端末の情報は、**記録するが管理しない**。セッションと監査ログに User-Agent・IP・地域（Cloudflare の `cf.region`。追加コストなし）を残し、事後に「いつ・どこから・何で操作されたか」を辿れるようにするだけに留める。

### 3.11 「端末の貸し借り禁止」をどう担保するか

**担保するのはパスキーそのもの。** `userVerification: "required"` により毎回 Face ID / 指紋 / 端末 PIN が要る。端末を貸しても、**本人の生体を貸すことはできない**。使わせるには端末パスコードごと教える必要があり、それは「貸し借り」ではなく資格情報の譲渡で、就業規則の領域になる。

技術側で追加するのは最小限の2つだけ。

1. **監査ログ** — 誰がいつ何を操作・閲覧したかを全件記録する。事後の追跡と抑止はここが担う
2. **管理者による全セッション強制失効** — 退職・端末紛失時に1操作で遮断できる

> 営業上の説明: 「**技術で防ぐのは『本人以外が使えないこと』まで。その先は記録で担保します**」。できることとできないことの線引きを明示するほうが、過剰な約束をするより信頼される。

セッション失効は即時性が要る。**KV は結果整合（最大60秒の伝播遅延）なので使わない。** D1 で処理する。

> **拡張余地**: セッションと監査ログに IP・地域が入っているので、「5分以内に離れた2地点から操作された」といった異常検知は**後からデータを足さずに実装できる**。デモの初版では作らない。

### 3.12 共用端末の扱い

「端末の貸し借り禁止」の唯一の例外が**打刻用の固定端末**。これは誰の端末でもなく、認証もせず QR を読み取るだけ（→ 6.3）。個人アカウントでログインする端末を複数人で共用することは、設計上も運用上も許可しない。

### 3.13 ステップアップ認証

**再認証を求めるのは、毎日最初の打刻だけ**にする。

打刻は労務記録なので「本人が打った」ことに意味がある。ログイン済みの端末を貸したまま
代打ちされると記録の意味が消えるが、毎回求めると1日に何度も生体認証が要る。
そこで**その日の1件目の打刻だけ**に絞る。2件目以降（退勤・現場移動）は素通しする。
日付の境界は日本の業務日で切る（→ 6.3 の未出勤の切り替えと揃える）。

**ボタンを押させない。** 打刻を押した流れのまま Face ID が出て、成功したらそのまま
打刻が続く。利用者から見える操作は「打刻」の1つだけで、再認証は途中に挟まる。
「再認証する」ボタンを押してから操作をやり直す形にすると、押し忘れて行き止まりになる。

打刻端末経由（QRを読み取る経路）には効かない。**あの打刻は端末のセッションで動き、
本人のセッションが無い**ため。QRが30秒で失効すること自体が本人の証明になっている。

給与・請求・利用者管理・パスキー削除・監査ログには**求めない**。
一度そうしていたが、5分の窓が入力中に切れて保存できないだけの障害になり、
再認証の手段が同じ画面に無い経路では行き止まりになった。
判定の仕組み（`needsStepUp` と `/auth/stepup/*`）は残してあるので、
必要になった操作の先頭でこの関数を呼べば復活する。

### 3.14 セッション

- D1 上のサーバ側セッション。**1ユーザーにつき複数本が並行して存在してよい**（上限は設けない）
- Cookie の中身は不透明なランダム 256bit のみ
- Cookie 属性: `__Host-sid=...; HttpOnly; Secure; SameSite=Strict; Path=/`
- **Max-Age を付けない**（セッション Cookie）→ ブラウザ終了で消える＝「起動の都度認証」
- モバイルブラウザは実際には終了しないので、**アイドル 15 分 / 絶対 8 時間**のタイムアウトで補う
- 職人ロールは出退勤しか使わないため、より短く（アイドル 5 分）してもよい
- **`terminal` ロールのみアイドルタイムアウトを適用しない**（絶対期限 30 日のみ）。固定端末が8時間で切れると現場が止まるため。業務データを一切表示しない端末であることが根拠
- 各セッションに `user_agent` / `ip` / `region` / 最終アクティビティ時刻を**記録のために**持つ（判断には使わない）
- 期限切れセッションの掃除は Cron Triggers で日次実行

本人の「ログイン中の一覧」画面は用意する。ただし表示は記録された値をそのまま出すだけで、端末を管理しているわけではない。

```
Safari / iPhone     渋谷区   5分前    ← 現在のセッション
Chrome / Windows    新宿区   30分前
                                    [すべてログアウト]
```

一括ログアウトのみとし、個別失効は作らない。端末紛失時に必要なのは「全部切る」であって、選んで切る操作ではない。

### 3.15 アカウント状態 — 稼働 / 停止

管理画面の区分別名前一覧からユーザーを1名選び、状態を切り替える。`users.status` は `active`（稼働）/ `suspended`（停止）の2値。**`retired`（退職）は今後検討**（→ 12章）。

#### 3.15.1 停止で起きること

**1. 即座にアクセス不能になる**

セッション解決のクエリが `users.status = 'active'` を条件に含む。**停止した瞬間、そのユーザーの次のリクエストから通らない。** 伝播遅延はゼロで、セッションを消して回る処理も要らない。

```sql
SELECT s.*, u.role FROM sessions s
  JOIN users u ON u.id = s.user_id
 WHERE s.id = ?1
   AND s.revoked_at IS NULL
   AND s.idle_expires_at > ?2
   AND u.status = 'active'        -- ここ1行が停止の実装
```

セッションを D1 に置き、KV を使わなかった判断がここでも効く。KV なら最大60秒、停止したはずのユーザーが動き続ける。

**2. ログインできなくなる**

WebAuthn のアサーション検証が通っても、`status` が `active` でなければセッションを作らない。**パスキーは削除しない**ので、稼働に戻せばそのまま再ログインできる。これが「停止」と「退職」の違いになる。

**3. 端末側が消去され、ログアウトされる**

| 対象 | 手段 |
|---|---|
| セッション Cookie | `Set-Cookie: __Host-sid=; Max-Age=0; ...` |
| キャッシュ・ストレージ全般 | `Clear-Site-Data: "cache", "cookies", "storage"` |
| 表示中の画面 | **一覧の定期更新**で検知して強制遷移（下記） |

`Clear-Site-Data` は 2023年以降、主要ブラウザで利用できる。ただし**本設計は最初から localStorage も sessionStorage も Service Worker も使っていないため、消える対象が事実上存在しない**。保険として送るだけで、ここに依存はしない。

#### 3.15.2 表示中の画面を落とす — 専用のハートビートは持たない

停止しても、すでに開かれている画面はそのままでは消えない。Web アプリはサーバから能動的に通知できないため、クライアント側から定期的に問い合わせる必要がある。

**ただし専用の `/heartbeat` エンドポイントは作らない。** 一覧そのものを HTMX で定期的に部分更新し、**停止検知はその副作用として得る**。

```html
<div id="list"
     hx-get="/renraku/list"
     hx-trigger="every 60s"
     data-poll-pause
     hx-swap="innerHTML">
```

> **落とし穴（実装時に踏んだ）**: htmx のイベントフィルタ
> `[document.visibilityState==='visible']` は **CSP と両立しない**。
> htmx はフィルタ式を `new Function()` でコンパイルするため、
> `script-src 'self'`（`unsafe-eval` 無し）では `htmx:syntax:error` になり、
> **トリガーごと登録されない**。`hx-trigger="load, every 25s [...]"` と
> 書くと `load` すら動かず、画面が「準備しています…」のまま止まる。
> 一覧側は SSR の初期表示があるため**一見動いて見えるが、
> 定期更新は一度も走っていない**という気づきにくい壊れ方をする。
>
> 対策として `data-poll-pause` を付け、`public/poll.js` が
> `visibilitychange` で `hx-trigger` を退避・復元する。
> 復帰時は即座に1回取得して最新に追いつく。
>
> **`load` トリガーも使わない。** htmx と `poll.js` はどちらも `defer` で
> 実行順が保証されず、**読み込み時点で画面が非表示だと `load` を
> 取りこぼす**（スマホでタブを切り替えながら開く、Safari のタブ復元）。
> 一度取りこぼすと表示に戻しても `load` は二度と発火せず、
> やはり「準備しています…」で固まる。空で始まる要素には
> `data-poll-now` を付け、初回取得も `poll.js` に集約する。
> ただし QR は JavaScript に依存せず初回から確実に表示するため、
> SSR で生成してHTMLへ埋め込む。`data-poll-now` が必要なのは、
> 空で始まる打刻記録だけとする。

- 停止されていれば `HX-Redirect` で「利用が停止されました」画面へ強制遷移させる
- **同時に一覧の内容も更新される。** 通知を実装しない方針（→ 6.1）と噛み合い、新着が自動で反映される
- **差し替えるのは一覧部分だけ**なので、ヘッダーも入力中のフォームも消えず、スクロール位置も維持される

全体リロード（`<meta http-equiv="refresh">` 等）は採用しない。リクエスト数は同じでも SSR の再レンダリングで **CPU 10ms 枠**と D1 読み取りを消費し、**入力中のテキストが消える・スクロール位置が飛ぶ**という代償が大きすぎる。「放置された画面を落とす」ためだけに、使用中のユーザー全員が払う代償になる。

**適用範囲**

| 画面 | 方式 | 理由 |
|---|---|---|
| れんらく・やること一覧 | **部分更新 60秒** | 放置されうる。内容更新の実益もある |
| 案件情報・れんらく本文 | 部分更新 60秒 | 放置されうる。内容が機密 |
| QR 表示 | **不要** | 既に25秒で更新している。そこに相乗り |
| 管理画面 | **不要** | 操作が頻繁で放置されにくい |
| 打刻端末 | **全体リロード 5分** | 入力もスクロールもなく、業務データを表示しない。定期リロードで状態を確実にリフレッシュするほうが素直 |

**頻度の制御**

- `document.visibilityState === 'visible'` のときだけ動かす（QR 画面と同じ手法）
- 操作が続いている間は、その操作自体が停止検知を兼ねるため**最終操作から30秒経過してから開始**する
- アイドル 15 分のタイムアウトが最終的な保険になる

これで**タブ4枚でも日 3,000 リクエスト程度**に収まる。専用ハートビートを 30 秒間隔で置いた場合（日 11,520）から大幅に減る。

> **商談での見せ方**: 経営者の目の前で、管理画面から職人アカウントを「停止」にする。1分以内に職人側の端末が自動でログアウト画面に切り替わる。**「退職者や紛失した端末は、その場で切れます」**を口頭ではなく実演できる。デモで最も効く一場面になるはず。

#### 3.15.3 運用ガード

- 切替は**代表・工事責任者と総務・安全管理のみ**。ステップアップ認証（直前5分以内の UV）が要る
- **自分自身は停止できない**
- **最後の稼働中管理者は停止できない** — 全員停止で誰も復旧できなくなる事故を防ぐ
- 停止・再開の操作は監査ログに記録する（誰が誰を、いつ）
- **停止中のログイン試行も記録する** — 「停止した人がまだアクセスを試みている」が見えること自体に価値がある

#### 3.15.4 停止中ユーザーのデータ

停止は「アクセスを止める」であって「データを消す」ではない。

- 本人が発信したれんらく、割り当てられたやること、打刻履歴は**すべて残る**
- 新規のれんらくの宛先・やることの割当先の**候補からは除外**される
- 既存の割当は残り、管理画面に「担当者が停止中」として表示する

## 4. 端末に何も残さない

### 4.1 レスポンスヘッダ（Hono ミドルウェアの標準値）

```
Cache-Control: no-store
Pragma: no-cache
Referrer-Policy: no-referrer
X-Content-Type-Options: nosniff
Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self';
                         img-src 'self' data:; connect-src 'self';
                         form-action 'self'; frame-ancestors 'none'; base-uri 'none'
Permissions-Policy: camera=(), microphone=(), geolocation=(),
                    publickey-credentials-get=(self),
                    publickey-credentials-create=(self)
```

**画面ごとの例外は2つだけ。**

- `Permissions-Policy` は打刻端末モードの画面でのみ `camera=(self)` に緩める
- **現場作成・変更画面**だけは Google Maps のドメイン制限付き API キーを送るため、
  `Referrer-Policy: strict-origin-when-cross-origin` と nonce 付き CSP へ切り替える。
  URL のパスや入力内容は送らず、**オリジンだけを Google へ伝える**

> **実装時に踏んだ落とし穴（2件とも自分で設定したヘッダが原因）**
>
> - **`publickey-credentials-get` / `-create` を必ず `self` で許可する。**
>   `Permissions-Policy` を送ると、**明示しない機能は既定で拒否される**。
>   これを落とすとパスキーが `NotAllowedError` で即座に失敗し、
>   生体認証のプロンプトすら表示されない
> - **CSP の `form-action 'self'` は、`action` 属性の無いフォームを拒否する。**
>   ブラウザが送信先を判定できないため submit イベント自体が発火せず、
>   JavaScript のハンドラに到達しない。パスキー用のフォームにも
>   `action` を明示すること（実際の送信は JS が `preventDefault` する）

### 4.2 実装ルール

- **Service Worker を登録しない**（PWA 化しない。オフライン対応は要件と両立しないので捨てる）
- **localStorage / sessionStorage を一切使わない**。状態はすべてサーバ側。HTMX は DOM 差し替えだけなので自然に守れる
- フォームは `autocomplete="off"`
- **添付ファイルの配信**: D1 バインディングを持つのは API だけ。API が有効期限 60 秒・1回限りのトークンを発行し、SSR の `/f/:token` が API 経由で転送する。SSR は D1 を直接見ない
- `Cache-Control: no-store` により iOS Safari の bfcache 対象外になる。戻るボタンで前画面の内容が復元されない

### 4.3 no-store の適用範囲

「端末に何も残さない」は **機密情報に対する規則**であって、全ファイルに対する規則ではない。

| 対象 | ヘッダ | 理由 |
|---|---|---|
| HTML・API 応答・添付 | `no-store` | 業務データ。1バイトも残さない |
| `htmx.min.js`（版が固定） | `public, max-age=31536000, immutable` | 中身が変わらないので長期キャッシュしてよい |
| `app.css` / `webauthn.js` | `public, max-age=0, must-revalidate` | 開発中に頻繁に変わる。長期キャッシュにすると端末側に古い版が残り、**「直したはずの不具合が直らない」という調査困難な状況**を生む |

静的アセットまで `no-store` にすると、毎回ダウンロードが発生して**古い端末ほど体感が悪化する**うえ、無料枠のリクエストも無駄に消費する。得るものが無い。

### 4.4 防げないこと（正直に明示する）

- **スクリーンショット**は Web では防止できない。ネイティブアプリでも Android は `FLAG_SECURE` で防げるが iOS は完全には防げない
- 画面の**物理的な撮影**も当然防げない
- → 営業資料では「端末に**残らない**」と「端末に**映せない**」を明確に分けて説明する。抑止は監査ログと透かし（閲覧者名を薄く重ねる）で行う

## 5. フロントエンド方針

- **HTMX 2.x**（約 14KB gzip）＋ WebAuthn 用の自作スクリプト（数十行）のみ
- SSR は Hono の JSX。**クライアント側 React は使わない**（バンドルもハイドレーションも無い）
- ページ遷移は SSR、部分更新は `hx-get` / `hx-post` で HTML 断片を差し替え
- CSS は手書き 1 ファイル。フレームワーク不要
- JS が無効でも、主要操作は素の `<form>` として成立させる（プログレッシブエンハンスメント）
- iOS 16 / Android Chrome 108 を実機確認の下限とする

HTMX を選ぶのは、SPA より**古い端末で確実に動き、かつ端末に状態を残さない**から。要件と手段が一致している。

### 5.1 仕組みを利用者に見せない（実装時の決定）

**ホームには業務で対応するものだけを置く。** 端末一覧・パスキーの提供元・
同期バッジは `/settings` に移し、普段は目に入らないようにする。

当初はホームに「ログイン中の端末」「登録済みのパスキー」を並べていたが、
**職人が見ても判断材料にならない**。「iCloud キーチェーン」「Bitwarden」
「同期される」が並んでいても、意味がわからないものが表示されているだけで、
**私物端末を業務に使うことへの不安を増やす方向に働く**。

BYOD の提案では「難しそう」と思われた時点で負けるので、
**技術的に正しく作れたものを、そのまま見せない**。

| 画面 | 置くもの |
|---|---|
| ホーム「今日」 | 当日の日付 / 自分宛の未読れんらく / 担当作業 / 現場 / 現在の打刻状態 |
| トップバー | ai番頭さん / 利用者名 / 全機能 |
| `/more` | れんらく / やること / 全員の出退勤・入退場 / 現場 / 営業・集金（権限がある人だけ） / 労働時間 / 管理 / 設定 |
| `/settings` | ログアウト、ログイン中の端末、全端末ログアウト、パスキーの追加 |
| `/settings` の折りたたみ内 | パスキーの提供元・同期バッジ（**商談での説明用**） |

### 5.2 業務アクションセンターとして見せる

ホームを機能リンクの一覧にはしない。**利用者が次に処理すべきものを先頭に出す**。

- 「やること」へ、自分が担当する未完了作業を期限切れ・再確認・期限順で3件表示し、今日が期限のものは3件を超えてもすべて表示する
- 「やること」の上へ「れんらく」を置き、自分宛の未読を件数制限なしですべて表示する
- れんらくの「すべて見る」から、既読を含むれんらく一覧へ移動する
- 「すべてのやること」から、自分が担当または作成したやることを状態別に全件確認できる
- 見出しは利用者名ではなく「今日 M月D日（曜日）」とし、右端に現在状態を配置する。未打刻・退勤済みはグレーの「未出勤」、出勤中はブルーの「出勤中」とし、協力会社は「未入場／入場中」とする。タップすると現在状態に応じて出勤・退勤または入場・退場を行う
- 管理者の業務情報は「営業 → 現場 → 集金」の順で表示する
- 「今日」の営業・現場・集金・やることは、自分が担当に含まれるものだけを表示する
- ホームのカードに**担当者は出さない**。自分が担当のものだけが並ぶので、名前を読んでも判断が変わらず場所を取るだけだった
- 代わりに「問題発生 → れんらく → やること」を**この優先順**に、それぞれ1行（溢れは末尾を `…` で切る）で置く。止まっているものが最も強く、次が読めばよいもの、最後が自分の手を動かすもの
- 先頭に記号を付けて区別する。問題発生＝警告（赤）、れんらく＝スピーカー（黄）、やること＝実行（青）。記号は絵文字ではなくSVGで描き、端末による見え方の差を作らない
- 社員は各機能の「すべて見る」から、権限内の全件を確認できる
- 協力会社は「すべて見る」でも担当現場と、その現場のやることだけに限定する
- 協力会社員は、れんらくと労働時間を表示せず、担当現場・担当作業・入退場だけに限定する
- 作成操作は各機能の「すべて見る」から一覧へ進んだ先に表示する

画面領域を広く使うため固定フッターメニューは置かず、トップバー右端の「全機能」から
利用可能な機能を一覧表示する。打刻端末ロールはトップバーの「全機能」を持たず、
ログイン直後に `/terminal` へ移動する。
業務画面のトップバーは上方向へページを進めると画面上へ隠し、下方向へ戻すと再表示する。
画面先頭では常に表示し、作成・変更画面の操作バーは空いた位置へ詰める。

単一の入力内容を保存する画面は、共通操作として画面上部の左に「戻る」、右に
作成画面では「保存する」、変更画面では「変更を保存」を配置し、長いフォームでも
保存操作を探させない。保存前の選択だけを行う中間画面は、右側を「次へ」とする。

### 5.3 「戻る」とパンくずを全画面に置く

ホームを除くすべての画面で、見出しの左上に「戻る」と、その右にここまでの
パンくずを置く。それまで小見出し（「現場別」「作業を確実に完了」など）が
占めていた位置をこれが引き継ぐ。飾りの文言より道のりのほうが常に役に立つ。
保存操作を持つ作成・変更画面は上部の操作バーが既に「戻る」を持つので、そちらを使う。

トップバー左端の「ai番頭さん」は、どこからでもホームへ戻る役割を持ち続ける。
「戻る」はこれとは別の操作なので、見た目でも位置でも分ける。

現在の画面はパンくずの末尾に並べない。直下の見出し（h1）と同じ文言が2度出るだけで、
押せる項目でもない。階層が深いときは折り返さず横スクロールさせる。折り返すと
見出しの上の高さが画面ごとに変わり、同じ位置にあるはずの h1 が上下する。

**画面末尾にも同じ「戻る」を置く**（`BackLinkFooter`）。現場詳細やれんらく詳細は
読み終えた位置が画面の下にあり、そこから先頭まで戻らせるのは手数が多い。
行き先は上部とまったく同じにする。末尾にパンくずは置かない。
そこで現在位置を示す必要はなく、出口が1つだけのほうが迷わない。

かつて各画面の末尾にあった「現場一覧へ戻る」などの個別リンクはこれに置き換えた。
上部の「戻る」と役割が重複するうえ、**経路を持たないので押すとパンくずが切れる**。
ただしエラー画面（404・403）には上部の「戻る」を置いていないので、
そこの末尾リンクは残す。

行き先は**履歴ではなくリンクで示す**。`history.back()` は QR やブックマークから
直接開いたときに行き先を失い、htmx の部分更新も履歴に混ざる。リンクなら常に定まる。

遷移元（`Referer`）は使えない。**この設計は `Referrer-Policy: no-referrer` を
全ページへ送っている**ため、ブラウザは遷移元を一切通知しない（→ 4章）。
端末に何も残さない方針の一部なので、「戻る」のためにこれを緩めることはしない。

そこで**経路を `?nav=` で URL に持ち回る**（→ `ssr/src/views/BackLink.tsx`）。
`?nav=more.places` なら「全機能 → 現場一覧 → 今ここ」を表す。

- 一覧や詳細へのリンクは、自分を経路の末尾に積んで渡す（`navTo`）
- フィルタタブなど自画面へのリンクは経路をそのまま引き継ぐ（`navKeep`）
- 「戻る」は経路の末尾。経路が無ければ画面ごとの既定値へ
- パンくずの各項目は自分より手前の経路を持つので、途中へ戻ってもさらに戻れる

**経路に積めるのはパスが固定の画面だけ**で、`BackLink.tsx` の `ENTRY_POINTS` に
列挙する。現場詳細のように URL に ID を含む画面は積まない。行き先を URL から
丸ごと受け取ると、他人の現場番号を書いたリンクを踏ませる余地が生まれるためである。
知らない値・循環・深すぎる経路は捨てるので、行き先は常に既知の画面に限られる。

ID を含む画面を1段だけ挟みたい場合は、**行き先を表示側が自分で組み立てて**
`BackLink` の `trail` に渡す。ID の出どころで2通りある。

- 現場れんらく詳細のように、現場 ID が**自分の URL パスの一部**なら常に挟む
  （`placeTrail`）。パスの一部なら他人の番号を差し込まれてもその画面が開けない
- やること詳細のように、経由元が現場かどうかは URL でしか分からない場合は、
  リンクに `?via=place` を付けて**経由したことだけ**を伝える（`viaTrail`）。
  現場 ID と現場名は、やることが API から受け取った**自分の値**を使う。
  これなら他人の現場番号を URL に書かれても行き先は変わらない

どちらも行き先そのものを URL から受け取らない。経路に載るのは常に
「今この画面を出している側が知っている値」に限られる。

作成・変更画面はパンくずを出さない（上部の操作バーが既に「戻る」を持つ）が、
**経路は素通しする**。ここで切れると、保存して詳細へ戻った瞬間に道のりが消える。

- 詳細の「変更」リンクは経路を渡す（`navKeep`）
- 操作バーの「戻る」は受け取った経路を戻り先に付ける
- **保存後のリダイレクトが問題になる**。POST の URL には `?nav=` が付かないので、
  `FormActionBar` が経路を隠しフィールドでフォームへ載せ、
  POST 側は `navFromForm` で行き先に付け直す

隠しフィールドの値も `navPath` と同じ検査に通すので、送られてきた値が汚れていても
行き先は既知の画面に限られる。

### 5.4 日付は略記で打てるようにする（実装時の決定）

`type="date"` をやめ、**テキスト欄＋カレンダーボタン**に統一する。
`type="date"` はブラウザ標準UIに固定されるため、
「8/12」「812」のような略記を受け付けられない。

現場で親指で打つので、区切りも年も省けることを優先する。

| 入力 | 解釈 |
|---|---|
| `8/12` `8-12` `8.12` `8月12日` | 月日。年は推定 |
| `812` `0812` | 3〜4桁は MMDD として読む |
| `2026/8/12` `2026-08-12` `2026年8月12日` | 年月日 |
| `20260812` | 8桁は YYYYMMDD |

全角（`８/１２`）も通す。弾くと、原因が分からないまま入力できなくなる。

**年の推定は「過去になるなら翌年」。** 12月25日に「1/5」と打てば翌年1月5日。
期限や予定は未来を指すことが多い。過去の日付（入金日など）は年から打つ。

#### 5.4.1 表示は「年/月/日（曜日）」で統一する

読むほうも全画面で揃える。`2026/8/12（水）`。

**曜日を出す。** 日付だけでは「12日って何曜日だっけ」で手が止まり、
予定を決める会話がその場で進まない。

**年も省かない。** 期限・入金日・工期は年をまたいで並ぶことがあり、
「1/5」だけでは今年か来年かが読み手に委ねられる。
画面ごとに `08/05` と `8/5` が混在していたのも直した。
**どこで見ても同じ形**なら、読み方を覚え直さなくてよい。

整形は `formatDateLabel` の1箇所だけが行う。以前は
やること・営業・集金・ホーム・現場がそれぞれ独自に切り出していて、
桁揃えも区切りもばらばらだった。

入力欄でも打った直後に同じ形を下に出す。読み取れない文字列は
その場で警告に変える。保存時まで気づかないと直す気が失せる。

#### 5.4.2 解釈はサーバーが行う

`views/date-input.ts` の `parseDateInput` が唯一の判定で、
SSR が `YYYY-MM-DD` へ直してから API へ渡す。**API は変更していない。**

画面側（`date-field.js`）は同じ規則を写しているが、
**保存される値は決めない**。打ちながら曜日を見せるためだけに持つ。

hidden に正規化した値を入れて送る案は採らない。
JS が動かない端末では hidden が更新されず、
**打った内容が無視されて古い値が保存される**——これが一番危ない。
入力欄そのものが `name` を持ち、略記のまま送ってサーバーが解釈する。

> 規則を2箇所に持つのは重複だが、サーバーだけに置くと入力中に曜日が出せず、
> 画面だけに置くと JS 無しで略記が保存できない。
> **ずれても困らない側（表示）を画面が持つ。**

### 5.5 保存に失敗しても入力を消さない（実装時の決定）

作成・変更の保存が失敗したとき、**エラー画面へ遷移させない**。
遷移すると「戻る」で入力が消え、件名から担当者まで全部書き直しになる。

弾かれる理由は「担当者を選んでください」のような**普通に起こりうる入力ミス**で、
異常事態ではない。長いフォームを埋めた直後にそれで全消えるのは、
入力そのものを避ける動機になる。

`data-inline-submit` の付いたフォームを fetch で送り、
サーバーは `Accept: application/json` のとき成功で `{ redirect }`、
失敗で `{ error }` を返す（→ `wantsJson`）。失敗時はエラー欄だけ更新し、
DOM はそのまま残るので入力は失われない。

対象は**入力量の多い6画面**（やること・現場・営業・集金の作成／変更）。
れんらくは送信前の独自チェックがあるため `renraku-form.js` が同じ役割を担う。

#### 5.5.1 JSON が返るとは限らない

500 や経路の取り違えでは HTML が返り、`response.json()` が構文エラーを投げる。
そのまま表示すると「Unexpected token '<'」という、
**利用者にとって何の意味も無い文字列**が出る。読めなかったときは状況で振り分ける。

| 状況 | 表示 |
|---|---|
| 400 | API のメッセージ（「担当者を選んでください」） |
| 401 / 403 | 「権限が確認できませんでした。画面を開き直してください」 |
| 500・JSON 不正 | 「保存できませんでした。時間をおいて試してください」 |
| 200 だが行き先が読めない | 「保存は完了しましたが、画面を移動できませんでした」 |

最後の1行が要る。**保存は済んでいるのに失敗と誤解させると、二重に登録される。**

**JS が無効なら通常の POST として動く。** その場合は従来どおりエラー画面へ
遷移する（入力は消えるが、保存できなくなるわけではない）。

> **実装時の落とし穴**: `run_worker_first: true` のため、
> 新しい静的ファイルは `app.get('/form-submit.js', …)` を足さないと 404 になる。
> public へ置くだけでは配信されない。

### 5.6 必要十分な情報だけを届ける

画面はデータベースの全行を見せる場所ではなく、**役割ごとの判断と次の行動を支える場所**とする。

- 権限外・担当外の情報は画面で隠すだけでなく、APIとSQLの段階から取得しない
- 未回答・期限切れ・再確認・打刻漏れを通常データより先に表示する
- 正常な全件一覧と履歴は折りたたみ、必要なときだけ展開する
- 対応対象が無い場合は空白にせず、正常であることを短く明示する
- 色だけに頼らず、状態名と件数で判断できるようにする
- 各画面の強い操作は、その利用者が次に行えるものだけを表示する

**ログアウトもホームには置かない。** セッション Cookie に `Max-Age` を
付けていないため**ブラウザを閉じれば消え**、アイドル15分でも切れる（→ 3章）。
自分のスマホを使う職人が押す理由が無く、押されると次回の生体認証が増えるだけ。
共用PCを離れるときのために設定の中には残す。

同期バッジは BYOD の核心（→ 3章）なので消しはしない。**畳んで残す**。
デモの場面2（→ 9章）では開いて見せられる。

副次的な効果として、**ホームで WebAuthn のライブラリ（22KB）を
読み込まなくなった**。パスキー追加が必要なのは `/settings` だけで、
職人は一度も開かない可能性が高い。

### 5.7 ホーム画面へ追加する

私物スマホのホーム画面から1タップで開けるようにする。**アプリは配らない**ので、
`manifest.webmanifest` と `apple-touch-icon` だけで済ませる（→ 4章の「端末に何も残さない」に反しない。
アイコンと定義ファイルは機密ではない）。

アイコンの原本は `ssr/scripts/AppIcon-source.svg` の1つだけで、
PNG は `build_icon.sh` が書き出す（手で PNG を編集しない）。
地はブランド色で全面を塗り、**角丸は付けない**。iOS・Android・ブラウザが
それぞれの形に切り抜くため、こちらで丸めると角が二重に落ちる。
Android の maskable 対応も、全面塗りなら同じ絵を使い回せる。

**タブ用（16/32px）だけは別の原本**（`AppIcon-favicon.svg`）を持つ。
「ai番頭さん」は 32px で潰れて読めないため、「ai」に縮める。
小さいアイコンは読ませるものではなく、タブの中で見分けるための色と形。

`default-src 'none'` のままだと manifest の取得が拒否されるので、
CSP に `manifest-src 'self'` を足す（標準CSPと Google Maps 用CSPの両方）。

## 6. 機能設計

### 6.1 れんらく

**1対1を作れない確認型スレッド**。LINE 代替ではなく、管理者を含む複数人で判断と回答を残すことに特化する。

- 発信権限: 代表・管理は全社、営業・自社技術者は宛先指定、協力会社は返信のみ
- **DM禁止**: 発信者を含む3名以上でなければ作成できず、発信者または「見る人」に代表・管理を必ず1名以上含める。発信者自身が代表・管理なら、別の管理者は必須にしない
- **回答方針**: れんらく単位で「見る人に回答を求める」または「回答不要」を選ぶ。個人別の回答指定は行わない
- **回答**: 回答を求める場合は見る人全員が OK / NG の2択で返し、必要な場合だけ20文字以内の返信を付けられる。未回答は全参加者に見せる
- **既読管理**: 誰が何時何分に読んだかは記録し、発信者は一覧で既読・未読件数を確認できる
- **回答必須は答えるまで未読のまま残す**（→ 下記）
- 参加者: 全社 / ロール / 複数人を指定。個人指定でも3名未満にはできない
- 協力会社は、自分が参加者に含まれるスレッドしか存在を知れない
- 添付画像は D1 の BLOB（1MB上限）+ ワンタイムトークン。閲覧すると監査ログに残る

一覧は新着順だけで見せず、初期表示を「要対応」とする。

- **要対応**: 自分が指名されて未回答、または未読のれんらく
- **未読**: 自分がまだ開いていないれんらく
- **すべて**: 参加している全れんらく
- 各カードには必須回答の進捗を数値とバーで表示する
- 詳細では数値の概要欄や閲覧状況の別表示を置かず、「応答状況」を役割別の名前チップで示す
- 回答不要では未読を赤、既読を青で区別する。回答を求める場合は未回答を赤、OKを青、NGを黄で区別する
- 凡例は色ドットではなく、名前チップと同じ配色の文字カプセルで表示する
- 凡例は「応答状況」のタイトル行右側へ配置し、回答不要では「未読・既読」、回答を求める場合は「未回答・OK・NG」へ切り替える
- 回答不要の名前チップには既読・未読の文字を繰り返し表示しない
- 回答を求められた人は回答するまで赤のままとする
- 作成画面には「3名以上」「管理者を含む」「回答を求める場合は見る人全員がOK / NGで回答」の公開ルールを常時表示する
- 「見る人」は全員・役割別・個人のチェックで選び、全員または役割の見出しから一括でON / OFFできる
- 作成・変更のルール違反は画面遷移せずフォーム上部へ表示し、本文・見る人・回答方針の入力を保持する
- 作成画面は「本文 → 回答 → 見る人」の順に入力する
- れんらく・やること・営業・現場・集金の本文系自由記述は400文字までとし、画面とAPIの両方で検証する
- 主画面で「すべて見る」がある一覧は、セクションタイトルからも同じ一覧へ移動できる
- 発信者・代表・総務は本文・参加者・回答方針を変更でき、変更前後・変更者・変更日時を履歴へ記録する
- 参加者から外れた人は以後閲覧できない。過去の既読・回答記録は証跡として削除しない
- 変更履歴はそのれんらくを閲覧できる全員へ表示する
- 履歴がある場合だけ「変更あり　変更履歴を見る」を表示する
- 既存の変更指示は移行時に変更履歴へ引き継ぐ
- 発信者・代表・総務は変更画面の末尾かられんらくを取り下げられる
- 取り下げたれんらくは削除せず、取り下げた日時・実行者を変更履歴へ残し、変更や回答をできなくする
- 取り下げたれんらくは「すべて見る」だけに表示し、（取り下げ）と本文の取り消し線で示す

> デモの見せ場: 「LINEなら個別に聞き直す確認を、最初から管理者を含む場で回答必須にできます」と振り、指名2名のうち1名だけ未回答の画面を出す。

#### 6.1.1 参加者は発信・変更の保存時点で確定させる（実装時の決定）

**`message_targets` に、発信または変更を保存した瞬間の対象者を `user` 行として書き出す。**
「全社」「ロール」のまま保存して閲覧時に解決する方式は採らない。

後者だと、**あとから入社した人が過去の連絡の未読者として現れる**。
既読管理が意味を持つのは「最後に保存した時点で誰に宛てたか」が自動で動かないときだけで、
「未読3名」がある日勝手に4名に増える一覧は、労務の証跡として使えない。

参加者の解決時に除外するもの:

| 除外 | 理由 |
|---|---|
| `terminal` ロール | 業務データを表示しない端末。宛先に入れると既読が永遠に埋まらない（→ 6.3） |
| 停止中の利用者 | 読めない人を未読に数えると「未読が減らない」状態になる |
| 発信者自身 | 自分の連絡が自分の未読に出ると邪魔になる |

発信者は閲覧者数には含めるが `message_targets` には入れない。API は書き込み前に、`message_targets` の2名以上と発信者を合わせた3名以上であること、かつその集合に稼働中の `exec` または `admin` が含まれることを検証する。回答を求める場合は `message_targets` と同じ利用者を `message_mentions` へ書き出す。

#### 6.1.2 回答方針と回答を別テーブルで固定する

- `message_mentions` は「見る人に回答を求める」場合に見る人全員を記録し、「回答不要」では空にする
- `message_responses` は参加者ごとに1件だけ、OK・NG・20文字以内の任意返信・回答時刻を記録する
- 回答の INSERT は `message_mentions` に存在することをSQLの `exists` 条件に含め、回答不要の人や部外者はURLを直接叩いても回答できない
- 応答状況は作成者・代表・管理だけに見せる。一般参加者には自分の回答欄だけを見せ、他の人の既読・未回答・OK / NGはAPIから返さない

#### 6.1.3 回答必須は答えるまで未読として残す

読んだだけでは終わりにしない。**回答を求められている連絡は、回答するまで
未読として扱う**。開いた時点で未読が消えると、答えないまま一覧から見えなくなり、
発信者は待ち続けることになる。未読件数・未読タブ・カードの強調がすべて対象。

既読そのものは記録する。「読んだが答えていない」と「そもそも見ていない」は
発信者の応答状況画面では別物として要る。未読の扱いだけを変える。

バッジは**「未読」と「未回答」を同時に出さない**。未回答があるときは「未回答」
だけを出す。両方並べても同じことを2つの言葉で言っているだけで、
次にすべきことが回答だと一言で示すほうが早い。
表記は応答状況の凡例と同じ「未回答」に揃える（旧「回答必須」）。

現場れんらくは元から「回答必須」を回答するまで表示し続けるので、変更しない。

#### 6.1.4 指名と選択肢は必ず対で持つ（実装時の決定）

**回答必須（`message_mentions`）にするなら `answer_options` も要る。**
片方だけの状態は、利用者から見ると**回答できないれんらくが永久に残る**。

選択肢が空のまま指名だけ入っていると、

1. 画面には返信欄と「回答する」ボタンが出る（選択肢のラジオは0個）
2. 押しても POST 側が「このれんらくは回答を求めていません」で弾く
3. 回答が記録されないので、未回答として残り続ける

しかも「回答必須は答えるまで未読として残す」ため、**未読バッジも消えない**。
デモの日次生成でこれが起き、毎日2件ずつ回答不能なれんらくが増えていた。

対処は2つ入れた。

- 生成側で選択肢を必ず入れる（日次生成・`/demo/seed` の両方）
- **表示条件を POST 側の条件と揃える。** 選択肢が0件なら
  `canRespond` を false にし、押せないボタンを最初から出さない

2つ目が本質的な守りで、データが壊れていても
**「押しても何も起きないボタン」だけは出さない**。

#### 6.1.5 既読は「宛先である」ことを条件に記録する（実装時の決定）

本文を開いた瞬間に既読を書き込むが、**宛先でない人が開いても記録しない**。
発信者は自分の連絡を何度も開くので、そこで既読が付くと既読数が実態とずれる。

D1 にトランザクションが無いため（→ 12.2-9）、判定と挿入を1文にまとめている。

```sql
insert into message_reads (message_id, user_id, read_at)
select ?1, ?2, ?3
 where exists (select 1 from message_targets
                where message_id = ?1 and target_id = ?2)
on conflict (message_id, user_id) do nothing
```

`on conflict do nothing` により、**既読時刻は最初に読んだ時刻のまま動かない**。
再読で更新されると「いつ読んだか」の証跡にならない。

#### 6.1.6 見える範囲は JOIN そのものが決める（実装時の決定）

「協力会社は自分が宛先の連絡しか存在を知れない」は、
ロールを見て分岐する処理では実装していない。
一覧クエリが `message_targets` を JOIN しているため、
**宛先でなければ行が返らない**。条件を書き忘れて漏れる余地が無い。

宛先でない連絡を URL で直接開いた場合も、存在しない ID と**同じ 404** を返す。
403 と 404 を区別すると、ID を総当たりして「存在するかどうか」を探れてしまう。

#### 6.1.7 通知はサンプルの対象外

**新着通知は実装しない。** Service Worker を使わない決定により Web Push が使えず、メール/SMS も本サンプルの範囲外とする。**利用者が画面を頻繁に見る前提**で運用する。

そのぶん、気づきやすさは画面側で補う。

- **一覧の60秒部分更新（→ 3章）が、そのまま新着の反映になる。** 停止検知と内容更新を1本のリクエストで兼ねているため、**通知のための追加リクエストがゼロで済む**
- 未読バッジは、その部分更新のレスポンスに含めてヘッダーへ反映する（`hx-swap-oob`）
- ログイン直後の初期画面をれんらくにする

商談で必ず問われるので、「サンプルには入れていませんが、通知は専用アプリで対応します」と即答できるようにしておく。**通知とカメラ連携が専用アプリ（→ 11章）の存在意義**になるため、話の流れとしてはむしろ都合がよい。

### 6.2 やること

- 作成・割当は代表・管理・営業に加え、自社技術者も担当現場に限り行える。協力会社は自分の割当分の完了報告のみ
- 状態: 未着手 / 進行中 / 完了 / 再確認
- 完了時はコメントを必須にし、押し間違いを防ぎながら直近の完了報告を残す
- 再確認時は理由を必須にし、理由・依頼者・依頼日時を表示する
- やることは変更でき、変更者・変更日時・項目ごとの変更前後を変更履歴へ記録する
- 変更履歴は管理者限定にせず、そのやることを閲覧できる全員へ表示する
- 履歴がある場合だけ「変更あり　変更履歴を見る」を表示し、履歴がなければ操作自体を表示しない
- 既存の変更指示は移行時に変更履歴へ引き継ぐ
- やることは取り下げず、中止する場合も本文へ「この作業は中止です。完了報告してください」などと明記して担当者が完了報告する
- 中止の経緯は通常の変更として変更履歴へ残す
- 期限超過をダッシュボードで強調
- れんらくから「やること」を起票できる導線を持たせる

一覧の初期表示は「未完了」とし、「期限切れ」「完了」「すべて」を切り替える。
詳細では状態と担当を先に示し、担当者・作成者それぞれに許された次の操作だけを表示する。
変更は代表・総務・営業が行い、営業は営業・現場のやることだけを変更できる。集金は担当に入っていれば営業も変更でき、社内の変更は代表・総務に限定する。

やることは営業・現場・集金・社内を横断する共通機能とし、`related_type` と `related_id` で関連先を表す。主画面・一覧・詳細では、題名の次行へ関連先の種別ラベルを置き、その直後に関連先名を表示する。業務ごとに別の作業一覧は作らない。

- 作成時は最初に営業・現場・集金・社内から関連先を選ぶ
- 営業・現場・集金の詳細から作成する場合は関連先を選択済みにする
- 営業の担当者候補は営業案件の担当者、現場は現場担当者、集金は管理担当者、社内は社員に限定する
- 集金と社内のやることは代表・総務だけが作成できる
- 自社技術者が作成できる関連先は、自分が担当する現場だけに限定する
- 関連先の種別と対象はAPI側でも検証し、画面から候補外の担当者IDを送っても登録しない
- 作成画面には「半日以内で、完了したか判断できる大きさ」を要約表示し、「？ ヘルプ」で粒度の判断基準と例を展開する

#### 6.2.2.1 関連先としての現場（詳細は → 6.7）

やることの関連先になる現場の仕様。**現場機能そのものは 6.7 で扱う。**

- 代表・総務・営業は現場を新規作成できる
- 現場の作成・編集時に担当者を分類別の複数選択で登録・変更できる
- 協力会社の人は協力会社マスタから所属会社を選んで招待する（社員／パートの区分は持たない）
- 現場担当には営業社員1名以上と管理社員（代表・総務）1名以上を必須とする
- 現場詳細の担当者名は独立した節を持たせず、**現場情報の中の見積工数の下**に一項目として置く。実務者を主表示、管理社員を右側の括弧内へ控えめに表示する
- 営業・現場・集金の一覧では、作成操作を「＋営業」「＋現場」「＋集金」に統一する
- 現場には住所、座標、現場注意・重要事項、見積工数を持たせる
- 「周辺注意」と「現場注意」は**1つ**（`site_notes` ＝ 現場注意・重要事項）に統合した（→ 0052）。書く側はどちらに書くか毎回迷い、読む側は結局両方を続けて読む。AI の申し送りも一覧の判定も常に2列を連結して扱っていた
- 現場の作成・変更は「現場注意・重要事項 → 現場の状態 → 問題発生 → 現場情報（現場名〜担当者）」の順に置く。安全に関わることを最初に書き、最初に読む
- **見積工数は社員までが見られる。** 原価に直結するため、協力会社の人にはAPIの段階で返さない
- 作業期間と現場連絡先も持たせ、訪問前に必要な情報を現場詳細へ集約する
- 座標があれば座標を、なければ住所を使って Google Maps を開く
- 現場作成・変更では住所をGeocodingし、拡大したGoogle Maps上のピンで座標を微調整する
- 地図のタップまたはピンのドラッグ終了時に緯度経度を自動入力する
- Google Maps用CSPは現場作成・変更画面だけnonce付きで許可し、他画面は従来の`self`限定を維持する
- ブラウザ用APIキーは`byod.sumpo.uk`と必要なAPIへ制限する

#### 6.2.3 見える範囲（実装時の決定）

| ロール | 見えるもの |
|---|---|
| 代表・総務・営業・自社技術者 | 全関連先の全件。「今日」では自分の担当・作成分だけ |
| 協力会社 | `place_members` に割り当てられた担当現場の全件 |

協力会社の絞り込みは、やることの担当者ではなく**現場割当の EXISTS**が担う。
担当現場では他担当者の進行も見えるが、状態を更新できるのは自分の担当作業だけとする。
担当外の ID を直接開いた場合も、
存在しない ID と**同じ 404** を返す。

> **実装時に見つけた不整合**: 実装は現場割当に加えて
> **「作成者か担当者か」も重ねて要求していた**（`getTaskFor` /
> `listTasks` / 期限切れ件数の3箇所）。この条件では、担当現場の
> メンバーでも自分に割り当てられていないやることが開けない。
>
> 結果、**現場詳細のやること一覧には出ているのに、タップすると
> 「やることが見つかりません」**になっていた。一覧は現場単位で出し、
> 詳細だけが担当者に限られていたため、見えているものが開けない
> 食い違いが生じていた。
>
> 上の表のとおり現場割当だけで判定するよう3箇所を揃えた。
> 更新側（`setTaskStatus`）は担当者・作成者の条件を持っており、
> 閲覧を広げても**書き込みは変わらない**。

#### 6.2.4 状態遷移も SQL の条件に含める（実装時の決定）

D1 にトランザクションが無いため（→ 12.2-9）、
「権限を確認してから UPDATE」の2手に分けない。
**条件付き UPDATE 1文**で、現在状態と実行者の資格を同時に判定する。

| 遷移 | 行える人 |
|---|---|
| 未着手・再確認 → 進行中 | 担当者 |
| 未着手・進行中 → 完了 | 担当者 |
| 完了 → 再確認 | **作成者**（完了報告を受けた側） |
| 進行中・再確認 → 未着手 | 作成者 |

代表・管理はどの遷移も行える。
**担当者が自分で再確認にはできない**（自分の完了報告を自分で否認する操作に
意味が無く、再確認は報告を受けた側の判断だから）。

API 側では権限判定を書かず、値の妥当性だけを見る。
二重に書くと、片方だけ直して食い違う事故が起きる。

#### 6.2.5 期限は「その日の終わり」まで

`YYYY-MM-DD` で受け取り、`YYYY-MM-DD 23:59:59` として保存する。
日付の 00:00 を期限にすると、**期限当日の朝に既に期限切れ**になり、
現場の感覚と合わない。

#### 6.2.6 期限は必須（実装時の決定）

任意だったのをやめる。**いつまでか決まっていないものは、やることにしない。**
期限が無いと一覧で並べようがなく、期限切れの強調も効かない。
「そのうちやる」は、やることではなく次の対応（→ 6.2.1）が持つ。

画面の `required` だけでなく**API 側でも必須にする**。
JS を切れば空で送れてしまうため、決めを守るのはサーバー側。

#### 6.2.7 入力は書く順に並べる（実装時の決定）

件名 → 内容 → 期限 → 関連先 → 担当者 の順にする。

最初に浮かぶのは「何をするか」で、**関連先や担当者はそのあとに決まる**。
先に選択肢を出すと、書きたいことを頭に置いたまま選ばせることになる。
変更画面も同じ並びにする。同じものを直すのに順序が違うと迷う。

作成画面にあった「担当と期限を明確に」の一文と、
やることの大きさを説明する折りたたみヘルプは外した。
**入力欄にたどり着く前に読ませるものが多いほど、書き始めが遅れる。**

#### 6.2.8 現場の完了もコメントを必須にする

現場の完了は**集金へ進む起点**なので、やることと同じくコメントを必須にする。
何をもって終わりとしたかが残っていないと、後から請求の根拠を確かめられない。

完了は現場詳細の「この現場を完了する」からだけ行う。変更画面の「現場の状態」
セレクトからは完了を外した。セレクトの一項目のままだと、他の項目を直した
ついでに完了してしまい、コメントを必須にした意味が無くなる。
完了済みの現場を変更するときは、その状態を保ったまま送り返す。

完了の操作は**画面末尾、「戻る」の上**に置く。完了は現場の内容をひととおり
見終えたうえで下す判断なので、上部にあると確かめる前に押せてしまう。

#### 6.2.9 完了コメントに下書きボタンを置く（実装時の決定）

コメントを必須にしても、**書き出しが面倒で「完了」とだけ書かれる**。
入力欄の下に「✦ AIサポート」を置き、下書きを入れられるようにする。

**AI は実際の作業結果を知らない。** 分かるのはやることのタイトル・本文・
現場メモだけなので、作れるのは下書きであって報告そのものではない。
振る舞いを2つに分ける。

| 入力欄 | 送る材料 | AI がすること |
|---|---|---|
| 何か書いてある | **メモを唯一の事実として渡す** | 言い回しを整えるだけ。メモに無い作業を足さない |
| 空 | やることの内容だけ | 指示内容を「〜しました」に言い換えた1文だけ |

##### 6.2.9.1 下書きは1〜2文、60文字以内

当初は「実施内容 / 確認結果 / 残件」の3行を指示していた。これが長さを生んだ。

```
実施内容：西町スーパー LED更新工事売場別の照明台数を現物と図面で照合し、
交換対象外の器具を含めて記録した
確認結果：
残件：
```

**作業名を丸ごと繰り返している。** やること詳細の見出しに書いてあることを
コメントでもう一度書いており、読む人にとって新しい情報は「照合し、記録した」
だけ。見出し形式そのものが、埋めるべき欄として文字数を要求していた。

指示を「1文、長くても2文。60文字以内」に変え、
**悪い例と良い例をプロンプトに書く**。

```
悪い例: 「西町スーパー LED更新工事売場別の照明台数を現物と図面で照合し…」
良い例: 「照合し、記録しました」
```

現場で親指で直す文なので、短いほど良い。`max_tokens` も 200 に下げ、
長い文が返ること自体を起きにくくしている。

ルールベース側も見出しを外した。**メモがあればそのまま返す** —
人が書いた文がいちばん短くて正確なので、飾りを足さない。

メモありを主に想定している。「配管直した。漏れなし」と書いてから押せば、
事実は人が供給しているので**捏造が起きにくい**（→ 6.9 で実際に起きた）。

指示では**何を作ってはいけないかを名指しする** — 数値、測定結果、
写真の有無、立会者名。これらが作られると、労務・品質の記録として残る。

生成物は入力欄へ直接入れ、そのまま編集できる。**保存はしない**（→ 4章）。
提出するのは人が直したあとの文で、ボタンの横に
「下書きなので、提出前に必ず確認してください」と常に出す。

ボタンは提出ボタンと形を変える（枠線だけの丸ボタン）。
**押しても提出されない**ことが見た目で分かるようにするため。
生成に数秒かかるので、押している間はラベルを「生成中…」に替えて無効化する。

伏せ字と一時停止スイッチはサマリーと同じ仕組みに乗る（→ 6.9）。
`AI_SUPPORT=off` やキー未設定のときは雛形が入る。

完了は変更履歴にも記録する（状態の変化と完了コメント）。

#### 6.2.10 やり残しがある現場は閉じられない

次のどちらかが残っていると完了できない。

- **回答されていないれんらく** — 回答必須の現場れんらくに未回答の担当者がいる
- **未完了のやること** — その現場のやることに完了していないものがある

未読は数えない。読んでいないだけで応答義務がなく、これで止めると
「既読を押させるための操作」が生まれて記録の意味が薄れる。
取り下げたれんらくも数えない（対応の必要が無くなっている）。

代表であっても例外は無い。抜け道を作ると、急ぐ場面で常にそちらが使われる。
やることは取り下げか完了報告で、れんらくは回答か取り下げで解消できる。

画面ではボタンを出さず、**残っている件数をそのまま表示する**。
消すだけだと「なぜ完了できないのか」が分からない。
ただし**判定の最終地点は API 側**（`completePlace`）に置く。
画面の制御だけでは、直接 API を叩けば通ってしまう。

#### 6.2.11 完了と同時に売掛を作る

現場が終われば請求が発生する。導線を出して人に作らせると作り忘れが起きるので、
**完了と同時に売掛を自動で作る**（→ 6.2.2）。すでに売掛がある現場では作らない
ので、完了をやり直しても増えない。

受注済みの営業案件が紐づいていれば、件名・顧客名・請求先・見積金額・担当者を
引き継ぐ。担当は**営業案件の担当**にする。請求先を知っているのはその人たちで、
現場を完了させた人（工事責任者かもしれない）ではない。

受注案件が無い現場でも売掛は作る。請求そのものを落とすほうが害が大きい。
ただし `collection_items` の金額・顧客名・請求先名は NOT NULL なので、
分からない項目には **「不明」** を入れる。集金一覧にそのまま出るので、
直すべきものが見て分かる。

完了後の現場詳細には、作られた売掛への「売掛を確認」を出す。

#### 6.2.12 「すべて見る」は終了したものを直近だけにする

一覧を無制限にすると、**終わったものが増えるほど進行中のものが押し出される**。
件数の上限（200件）だけでは順序が保証されず、しかも壊れ方が
「古いデータが見えない」ではなく「今やるべきものが見えない」になるため
気付きにくい。現場に至っては上限すら無かった。

そこで既定は「進行中は全件、終了は直近90日」とし、それ以前は**年を指定**して見る
（→ `api/src/store/list-scope.ts`）。対象と終了の基準日は次のとおり。

| 一覧 | 終了とみなす条件 | 基準日 |
|---|---|---|
| 現場 | `stage = 'completed'` | `completed_at` |
| やること | `status = 'done'` | `completed_at` |
| 営業 | `stage in ('won','lost')` | `updated_at` |
| 集金 | `stage = 'paid'` | `paid_date`（無ければ `updated_at`） |

**終了日時が無い行は既定では残す**。過去のデータで日時を持たないものを黙って
消すと、あったはずの記録が見えなくなる。年で絞ったときだけ、日時が無いものは
どの年にも属さないので外れる。

年の選択肢は直近5年を常に出し、データを数えて作らない。空の年を隠すために
毎回集計を走らせる価値がなく、選んだ結果が空なら「その年は無い」と分かる。

ホームは年を渡さないので常に既定の範囲になる。

### 6.2.1 営業

引き合いから受注までを営業内で共有し、受注した業務情報だけを現場へ引き継ぐ。

- 段階は「引き合い / 商談 / 見積 / 受注 / 失注」とする
- 一覧は進行中を初期表示し、各段階または全件へ切り替えられる
- 案件名、顧客名、営業メモ・重要事項、予定現場・住所など、顧客担当・連絡先、見積工数、見込金額、次の対応、対応日、担当者を持つ
- 入力順・表示順は作成・変更・詳細で揃える。案件名から始め、見積工数・見込金額・予定納期は**3つで1組**として同じ行へ並べる
- ただし営業メモ・重要事項は**次の対応の直後**に置く。詳細では先頭パネルの下段へ全幅で、作成・変更では次の対応の入力欄の下へ置く。次の一手と、その判断のもとになった話は続けて読み書きするため、連絡先や請求先まで下げない
- `planned_period` は画面上「予定納期」として扱う。受注時は現場の作業期間へ引き継ぐ
- 担当者には営業社員1名以上と管理社員（代表・総務）1名以上を必須とする
- 担当表示は「協力会社 → 自社技術者 → 営業 →（総務 → 代表）」の順とし、分類内は名前順、管理社員は右側へ括弧付きで表示する。**管理社員の文字サイズは左の実務者と揃え**、色と太さだけで控えめにする
- 営業・現場・集金の変更時は変更項目の変更前後、変更者、変更日時を追記保存する
- 変更履歴は代表・総務だけが、履歴がある場合に表示される「変更あり　変更履歴を見る」から日時降順で確認できる
- 請求先名、請求先区分（法人・個人）、請求先住所、請求担当・連絡先を営業時点で確認し、請求先名と区分は必須にする。**先に読むのは名前**なので区分より左へ置く
- 段階を変更した場合は変更者と変更日時を追記専用履歴へ残す
- 代表・総務・営業だけが一覧・詳細・作成・変更・現場転記を行える
- 自社技術者、協力会社、打刻端末にはAPIの段階から営業案件を返さない

#### 6.2.1.1 次の対応はディレクション、やることはアクション（実装時の検討）

**やることで賄えるのではないか**という指摘があった。実際に文面は重なる。
「次回打合せの資料を準備する」は、やることにしても成立する。

それでも両方を残す。**粒度ではなく種類が違う**ためで、
どちらも「これからやること」を書くから重複して見えるだけ。

| | 次の対応 | やること |
|---|---|---|
| 性格 | **ディレクション**（案件をどう進めるか） | **アクション**（誰が何を終わらせるか） |
| やる人 | **決めない。** 案件チームの誰か | **特定の1人以上**を指名する |
| 終わり方 | 次を書けば上書きされて消える | 完了コメントを残して閉じる |
| 例 | 「次は見積提出」 | 「総務が請求先情報を確認する」 |

担当者を決めないことが、次の対応の本質。方向が決まっていれば
誰がやるかは後で決まるし、決まる前に書けることに意味がある。

ディレクションだからこそ、**案件の並び順を決められる**。
`next_action_date` が営業一覧の並び順そのもので、
一覧は「次に動くべき順」になる。カードにも「次：見積書を提出」が出るので、
案件を開かずに読める。アクションは案件の中の作業なので、
案件同士の順序づけには使えない。

入力欄は**営業段階のすぐ下**に置く。段階を動かしたら次の一手も書き換える、
というのが実際の流れで、離れていると**段階だけ直して次の対応が古いまま残る**。
ディレクションなので、案件の状態を決める項目とまとめる。

詳細画面でも、段階・担当者と同じヘッダにまとめる。
以前はヘッダに「次の対応日」があり、その直下のセクションで内容と日付を
再掲していて、**同じ日付が2箇所に出ていた**。
ディレクションは1行で読めれば足りるので、専用のセクションは持たない。

内容と日付は**1つの枠に2行**で入れる。

```
┌────────┬──────────────┬────────┐
│  段階  │   次の対応    │ 担当者 │
│  商談  │ 見積書を提出  │ 前田他 │
│        │ 2026/8/13（木）│        │
└────────┴──────────────┴────────┘
```

並びは**段階 → 次の対応 → 担当者**。段階を見た次に読むのは
「で、次は何を」であって、誰がやるかはその後でよい。

「見積書を提出」だけでも「8/13」だけでも判断できず、
**必ず一緒に読む**もの。見出しを「次の対応」と「次の対応日」に
分けると、同じことを確かめるのに視線が往復する。

**やることの担当者は、その案件の担当者に限られる**（→ `sales_opportunity_members`）。
案件担当は「営業1名以上＋管理社員1名以上」が必須なので、
実質2〜3名のチーム内で作業を振り合う形になる。
社外や無関係な社員へ飛ばせないのは、案件の閲覧範囲と揃えるため。

> **商談での説明**: 「次の対応」は営業担当が案件の進め方を書く欄、
> 「やること」は**総務に書類確認を頼む**ような他人へ振る作業。
> 日次デモに出る「◯◯ 提出書類の確認（総務→営業）」がそのまま実例になる。

> **未決**: やることの最短期限を営業一覧の並び順に使えば、
> 「次の対応」を畳める。表示も「次：〈最短期限のやること〉」にできる。
> ただし**ディレクションをアクションに変換させる**ことになり、
> 担当が決まる前に方向だけ書く場が無くなる。
> 実運用で「次の対応だけ埋まってやることが空」が続くかを見てから決める。

受注した案件では、詳細の**先頭パネルの直下**に「受注から現場を作成する」パネルを出し、「＋現場を作成」を置く。
受注直後にやることは現場を起こすことなので、そこから始められるようにする。

**集金の作成は営業案件からは行わない**。受注した時点ではまだ請求できず、売掛を起こすのは現場が終わってから。
集金は現場の完了と同時に自動で作成する（→ 6.2.2）。既に在る場合だけ、営業案件から辿れるよう「集金を開く」を出す。
ただし完了前に請求を起こす必要がある現場もあるため、**現場詳細**に「＋集金を作成」も置く。
配置は「この現場を完了する」の行の右端とし、添え書きを2つのボタンの間に挟む。
自動作成が基本であることが伝わるよう、「完了と同時に自動で作成される。完了前に必要なときだけ使う」旨を添え、
説明を読んでから集金ボタンに届く順にする。
なお画面の文言では、記録そのものを指すときは**集金**に統一する。
「売掛」「請求」「入金」は集金の**段階名**（`receivable` / `invoiced` / `paid`）としてのみ使う。
先に作ってあれば完了時の自動作成は行わない（`collection_items.place_id` の件数で判定する既存の仕組みによる）。

現場から集金を作るときは `?from=place` を渡し、作成画面の「戻る」と保存後の行き先を**その現場**にする。
戻り先の現場 ID は、作成画面では選んだ営業案件が持つ `place_id`、保存後は**保存した集金が持つ** `place_id` から取る。
フォームから送られた ID をそのまま行き先にはしない（他人の現場番号を書いたリンクを踏ませないため）。
戻った時点で集金は作成済みになっているので、ボタンは「集金を開く」に変わる。

作成画面へ遷移する。現場は `/places/new?salesId=` で
案件名、住所、顧客担当・連絡先、見積工数、予定納期を初期値として入れ、**保存した時点で**案件と結ぶ。
即時に現場を作らないのは、現場名や住所を保存前に直せるようにするため。
営業メモ・重要事項と見込金額は営業情報に留め、現場へ引き継がない。現場担当者、座標、現場注意・重要事項は作成後の現場編集で設定する。
作成済みのものは、同じ場所でボタンを「現場を開く」に入れ替える。
この2つは `via=sales` を渡し、現場詳細・集金詳細の「戻る」を営業案件へ向ける（→ 5章の via）。
現場詳細から集金を開くときは `via=place` を渡し、集金詳細の「戻る」をその現場へ向ける。
集金は営業案件からも現場からも開けるので、集金詳細は**どちらの印で来たか**で戻り先を選ぶ。
戻り先の案件 ID と名前は、現場・集金が API から受け取った**自分の紐づき**を使う。
URL からは「営業を経由した」ことだけを受け取るので、他人の案件番号を書かれても行き先は変わらない。
営業案件の ID と名前は営業を見られる役割にだけ返す。
作ったかどうかがボタンの文字だけで分かり、作成済みのものを別の画面へ探しに行かずに済む。
作成済みかは現場が `sales_opportunities.place_id`、集金が `collection_items.sales_opportunity_id` で判定し、
集金は見られる役割にだけ出す。

転記は `sales_opportunities.place_id` の一意制約と、`place_id is null` を含む条件付き更新で二重作成を防ぐ。
受注前の案件や転記済みの案件を直接APIで結ぼうとしても拒否する。
現場の作成そのものは `/places` が行い、結ぶ処理（`/sales/:id/link-place`）は営業担当の引き継ぎと `place_id` の更新だけを担う。
結びに失敗しても作成済みの現場は残し、現場詳細へ送って営業側からやり直せるようにする。

### 6.2.2 集金

受注済み営業案件から、売掛・請求・入金までを管理する。

**閲覧は代表・総務に加えて営業にも開く。** 自分が取った受注が入金まで到達したかを、
経理へ聞きに行かずに追えるようにするため。営業は**全件を閲覧**できる。

**作成・変更は代表・総務が全件、営業は自分が担当に入っている集金だけ。**
金の動きを他人の案件にまで及ぼさせない。変更可否は**送られてきた担当者ではなく
DB上の現在の担当**で判定する（担当外の営業が自分を足した内容を投げるだけで
通ってしまうため）。協力会社員・自社技術者・打刻端末にはAPIの段階で返さない。

- 段階は「売掛 / 請求 / 入金」とする
- 売掛作成時は受注済み営業案件の選択を必須にする
- 集金担当には営業社員1名以上と管理社員（代表・総務）1名以上を必須とする
- 請求先は営業で確認済みの個人・法人情報をAPI側で再取得して引き継ぐ
- 集金画面から請求先を直接変更できず、変更する場合は元の営業案件を変更する
- 請求へ進める場合は請求日と、振込予定日または集金予定日の少なくとも一方を必須にする
- 入金へ進める場合は入金日を必須にする
- 段階変更は変更者と変更日時を追記専用履歴へ残す
- 新規作成は売掛から開始し、売掛から請求、請求から入金の順だけを許可する
- 請求中の予定日超過を一覧で強調する
- 営業案件と現場を任意で相互に開けるようにする
- 自社技術者・協力会社員・打刻端末にはAPIの段階から集金情報を返さない（営業には開く）

管理者の「今日」では営業を現場の上、集金を現場の下に配置し、自分が担当する未入金の件数と直近3件を表示する。

### 6.3 名簿（出退勤・入退場）

「全機能」の**名簿　（出退勤・入退場）**は打刻画面への入口にせず、全利用者について今日の
状態を区分別の名前一覧で表示する。**この一覧は社員だけが開ける。** 協力会社の人には
「全機能」に入口を出さず、APIの段階でも返さない（自分の打刻は今日画面から行う）。
**協力会社員は所属会社ごとにまとめ、省略名を見出しにしてインデントし、その右へ名前を並べる。**
見出しの幅は揃えて、会社が変わっても名前の先頭位置が動かないようにする。
8社ぶんの名前が混ざって並ぶと誰がどの会社の人か読めないため、会社で区切る。
名前は `記号＋名前` を**スペースなしで詰めて**表示する（例: `UMD梅田`）。
日付が変わり当日の打刻がなければ社員は未出勤、協力会社は
未入場とする。未出勤・未入場は赤、出勤・入場中は青、退勤・退場済みはグレー、
承認済み有給休暇で当日の打刻がなければ休暇として緑、稼働停止中は紫で表示する。状態は名前の横に
文字で添えず、カプセルの色だけで示す（凡例で色の意味を示す）。
名前をタップすると画面遷移せずポップアップを開き、当日の打刻時刻、出勤・退勤または
入場・退場、打刻場所を時刻順に表示する。打刻操作は今日画面の状態ボタンから行う。

**代表・総務には、このポップアップがそのまま利用者管理になる。** 名前の変更、稼働停止・
開始、再認証を同じポップアップの中で行い、協力会社の人には所属会社を協力会社マスタから
選ばせる。**管理画面に「利用者の名前・稼働状態を管理」の別枠は持たない。** 見る場所と
変える場所を1つにすると、19名規模では画面を行き来せずに済む。
停止の効き方（`resolveSession` の1行）と再認証の要求は3章のまま変わらない。

#### 6.3.1 協力会社マスタ

会社そのものの情報は利用者行から独立させ、`partner_companies` に持つ。記録するのは
会社名、**省略名**（10文字以内）、**記号**（英大文字3字以内）、住所、電話、メール、
主担当（自社側の窓口社員）、副担当（先方の担当者名）、契約重要事項、支払条件。

省略名は名簿の見出しに使い、記号は名前の前へ詰めて付ける（`UMD梅田`）。
一度は絵文字1字にしたが、社数が増えると見分けが付かず、白黒印刷や古い端末で崩れる。
業界の慣習どおり英字の記号に戻した。記号は小文字で入力されても大文字へ寄せる
（表記揺れで別会社に見えるのを防ぐ）。
契約重要事項と支払条件を含むため、**代表・総務以外にはAPIの段階で開かない**。

会社や常設現場では **「スマホが QR を表示 → 会社設置の固定端末が読み取る」**。
打刻端末がない場所では、本人の認証済み端末から場所を指定して直接打刻する。

#### 6.3.2 現在地から場所を選ぶ

打刻画面を開いた時点で位置情報を取得し、**担当現場の座標と照合して該当する場所を
選択状態にする。** 半径300m以内で最も近い現場を選び、**該当が無ければ「その他」**を選ぶ
（そこで初めて場所の手入力が要る）。半径を狭めると屋内で外れ、広げると隣の現場を拾う。

**打刻端末を経由しない打刻はすべて座標を残す。** 現場でも営業案件でも「その他」でも、
代表のワンタップ記録（場所を選ばない打刻）でも同じ。あとから「どこで打ったか」を
確かめる材料は、場所の選択有無に関わらず必要になる。
打刻端末経由（QRを読み取る経路）だけは対象外で、端末の設置場所が場所そのものを表す。

座標・精度は打刻と一緒に保存するが、**判定には一切使わない。**
GPSは屋内や地下で大きくずれるため、ずれを理由に打刻を拒むと現場が止まり、
労務記録に穴が空くほうが困る。位置情報が取れない・許可されない場合も打刻は通し、
場所を手で選んでもらう。利用者が自分で選び直した場合は、その選択を上書きしない。

打刻画面と、代表がワンタップで打刻するホームだけが `geolocation=(self)` を必要とする。
既定の `Permissions-Policy` は `geolocation=()` なので、打刻端末の camera と同じく
ハンドラ側で個別に開ける。

カメラ権限は BYOD スマホ側に要求しない（QRは表示するだけ）ので、標準ブラウザでの摩擦は小さい。

従業員側はQRより先に「出勤中」「退勤済み」「未打刻」の現在状態を表示する。
今日の履歴は自分の記録だけに限定し、管理者であってもこの画面へ他人の打刻を混ぜない。

協力会社は雇用上の出退勤と区別し、画面と打刻端末では `in` を「入場」、`out` を
「退場」と表示する。保存値は共通の `in/out` を維持し、既存の履歴・集計を分岐させない。
代表・役員は打刻場所の管理を不要とし、ホームの「出勤／退勤」を押すだけで記録する。
簡易打刻APIは `exec` ロールだけに許可し、場所選択画面やQRを表示しない。

打刻端末がない現場・在宅・営業先では、認証済みの本人端末から直接打刻できる。
打刻場所は本人が担当する進行中の営業、担当現場、その他から選択し、その他は
場所名の入力を必須とする。担当関係はAPIで再確認し、画面へ渡したIDをそのまま信頼しない。
出勤・退勤は従来どおり当日の最終打刻からサーバー側で自動判定する。履歴には直接打刻か
打刻端末かを区別して、選択時点の場所名を保存する。

```
[従業員のスマホ]                      [会社の固定端末 = PC-Web の打刻端末モード]
 SSR が QR を生成・表示                 BarcodeDetector API でカメラから読取
 25秒ごとに更新（画面表示中のみ）   ──→  読み取った文字列を API に POST
 3分無操作で自動停止                      └→ 検証OK なら打刻を記録し
                                             画面に名前を3秒表示して消す
```

打刻端末に出すのは**管理者が設定した名前のみ**（→ 3章）。所属は出さず、成功音とともに映像全体へ出勤は青、退勤は緑で大きく表示し、3秒で消す。端末の前に立てば誰が出勤済みか読めてしまう状態を作らないためで、`terminal` ロールのセッション寿命を長くしてよい根拠（業務データを表示しない）もこれで保たれる。

**QR ペイロード**: `userId | exp | random` をバイナリ化し、HMAC-SHA256（Web Crypto）で署名した短い文字列。UUID・期限・nonceを固定長で格納してQR生成器の容量内へ収める。署名鍵は Workers Secrets に置き、**API Worker だけが持つ**。

**QR の生成では DB に書き込まない（ステートレス）。** 署名だけで正当性が判定できるので、発行のたびに nonce 行を作る必要がない。書き込むのは**実際に打刻された 1 回だけ**。

リプレイ攻撃対策:
- 有効期限 **30 秒**（署名ペイロード内の `exp` で判定）
- 打刻時に `qr_used` へ nonce を **INSERT**。主キー衝突＝再利用として弾く（原子的）
- `qr_used` は Cron で 5 分より古い行を削除。常に数行しか存在しない
- 固定端末は設置場所が物理的に固定されているため、撮影した QR を別の場所で使うことも成立しない

**ポーリングの抑制**（無料枠対策）:
- 更新間隔 25 秒（有効期限 30 秒に対して余裕を1回分持たせる）
- Page Visibility API で、**画面が非表示のあいだは更新を止める**（`hx-trigger` を `every 25s [document.visibilityState==='visible']` で条件付けする）
- 3 分間スキャンされなければ自動停止し、「QRを再表示」ボタンに切り替える

対策前は 1 タブあたり 4,320 リクエスト/日（かつ同数の D1 書込）が発生しうる。対策後は 1 回の打刻あたり十数リクエスト・書込 1 行に収まり、100,000/日 の枠に対して桁違いの余裕ができる。

固定端末側は `BarcodeDetector` API（Chrome / Edge で利用可能）を使い、非対応ブラウザ向けに jsQR をフォールバックとして同梱する。**専用ハードウェアは不要で、余っている PC 1 台で動く** — これもコスト訴求になる。

読み取り端末は `terminal` ロールで認証済みであること（→ 1章）。未認証の端末からの打刻は受け付けない。
`terminal` ロールでログインした場合は、業務ホームを表示せず `/terminal` へ自動的に遷移する。

#### 6.3.3 打刻時刻はサーバ時刻を採用する

労務記録なので、**時刻の出所を1箇所に確定させる**。

```
スマホの時刻     → 使わない（利用者が自由に変更できる）
読み取り端末の時刻 → 採用しない（NTPずれの可能性がある）
サーバ時刻       → これを occurred_at とする   ← 唯一の正
```

読み取り端末の時刻は `terminal_reported_at` として**参考値だけ記録**し、サーバ時刻と一定以上ずれていたら管理画面に警告を出す。端末の時計狂いを検知する用途にのみ使い、打刻値としては採用しない。

打刻修正は総務・安全管理のみ。修正は必ず**元の値を残して**監査ログに記録する。

##### 6.3.3.1 出勤・退勤は自動で判定する（実装時の決定）

利用者に「出勤」「退勤」を選ばせない。**その日の直前の打刻が
`in` なら次は `out`** とサーバ側で決める。選ばせると、選び間違いが
そのまま労務記録の誤りになるうえ、打刻端末に操作を増やすことになる。

##### 6.3.3.2 元の値は最初の修正時にだけ記録する

`original_occurred_at` は `coalesce(original_occurred_at, occurred_at)` で
更新する。2回目の修正で上書きすると、**本来の打刻時刻が失われる**。
労務記録としては「何回修正されたか」より「最初に何時だったか」が重要。

#### 6.3.4 オフライン対応は行わない

施工現場が圏外になる可能性はあるが、**オフライン対応は見送る**。

理由は「端末に機密情報・個人情報は残さない、キャッシュにも入れない」という中心要件と両立しないため。画面をキャッシュすれば顧客名や住所が端末に残り、書き込みをキューに積むだけでも `no-store` と Service Worker 不使用の決定に例外を作ることになる。**要件の一貫性を優先する。**

- 圏外では打刻できない。エラーを明示して、**事務所での打刻修正（総務・安全管理）で運用的に吸収する**
- この割り切りは、専用アプリ（→ 11章）を用意する理由として説明に使える。通知とカメラ連携と合わせ、「だからアプリが要る」という話にまとまる

### 6.4 労働時間の集計（出退勤の上に載せる）

**新しい入力を1つも増やさず、`attendance_events` を集計するだけで成立する。**
打刻はすでに Phase 4 で取れているので、ここは読み取り専用の画面が増えるだけ。

労働時間の客観的把握は**労働安全衛生法66条の8の3で義務**であり、
「打刻はしているが集計は Excel で手作業」という会社が極端に多い。
**あると助かる機能ではなく、無いと違法になる機能**なので、
デモに足したときの説得力の伸びが6機能のなかで最も大きい。

管理者の初期表示は全員一覧ではなく、打刻漏れまたは時間外の注意対象だけとする。
正常な月次集計と全日次記録は折りたたみ、本人には自分の月間合計と日次記録だけを表示する。

#### 6.4.1 集計はテーブルを増やさない

日次・月次の集計結果を**保存しない**。`attendance_events` から都度計算する。

19名 × 月20日 × 2打刻 = 月800行で、1人1か月ぶんの集計は
**数十行の読み取りで済む**。集計テーブルを持つと打刻修正のたびに
再計算が要り、**修正漏れで集計と原本が食い違う**という最も避けたい
バグを作り込む。原本（`attendance_events`）を唯一の正とする。

CPU 10ms の制約（→ 2.4）に対しても、SQL 側で
`group by` して集計値だけを返せば JSX のレンダリング量は月31行に収まる。

#### 6.4.2 日をまたぐ勤務は「出勤の日」に属させる

夜勤・残業で 22:00 出勤 → 翌 5:00 退勤という打刻は普通に発生する。

```
勤務日 = その勤務の「出勤打刻の日付」   ← in と out のペアで1勤務
```

退勤日を基準にすると、夜勤が翌日の勤務としてカウントされ、
**現場の「昨日の夜勤」という感覚と合わない**。
日付境界で切ると1勤務が2日に割れて、どちらの日も実労働時間が
実態より短く出る。ペア単位で扱えばどちらの問題も起きない。

**`in` が2回続く／`out` で終わらないペアは「異常」として明示する。**
勝手に補完しない。打刻漏れは総務・安全管理が修正して直すもので、
システムが推測で埋めると労務記録の信頼性が根本から崩れる。
集計画面では該当日を警告色にし、`—` と表示する。

ペアリングは「次の `in` より前の、最初の `out`」を相手にする。
`lead()` で次の出勤を見るだけで、夜勤も打刻漏れも同じ1文で扱える。

```sql
with ins as (
  select id, occurred_at, substr(occurred_at, 1, 10) as work_date,
         lead(occurred_at) over (order by occurred_at) as next_in
    from attendance_events where user_id = ?1 and kind = 'in'
)
select i.work_date, i.occurred_at as in_at,
       (select min(o.occurred_at) from attendance_events o
         where o.user_id = ?1 and o.kind = 'out'
           and o.occurred_at > i.occurred_at
           and (i.next_in is null or o.occurred_at < i.next_in)) as out_at
  from ins i order by i.work_date
```

`out_at` が null の行がそのまま「打刻漏れ」になる。
**判定を別に書かなくても異常が浮く**形にしてある。
D1（SQLite）も Neon（Postgres）も `lead()` を持つので、
移植時に書き換えが要らない（→ 12.1.1）。

> **`next_in` の条件が本体（実装時に確認）**: これが無いと、
> 退勤を打ち忘れた日の出勤が**翌日の退勤とペアになる**。
> 8/04 に出勤だけして 8/05 に 21:00 退勤があると、
> **1勤務36時間**という記録が出来上がり、しかも
> 打刻漏れが「異常」として浮かばなくなる。
> ローカル D1 に打刻漏れを含むデータを入れて、
> 8/04 が `out_at = null` のまま残ることを確認済み。

#### 6.4.3 時刻の保存形式に合わせる

`occurred_at` は `nowIso()` により **`YYYY-MM-DD HH:MM:SS`（UTC・`T`無し）**
で保存されている（→ `api/src/store/types.ts`）。
集計側で差分を取るときは `T` と `Z` を補ってから `Date.parse` する。
**`Z` を付け忘れると実行環境のローカル時刻として解釈され、
時差のぶんだけ労働時間がずれる**。Workers は UTC で動くので
デモでは露見しないが、移植時に静かに壊れる種になる。

#### 6.4.4 休憩は差し引かない（デモの割り切り）

休憩打刻は作らず、**在社時間をそのまま実労働時間として表示する**。
かわりに「休憩は自動控除していません」と画面に明記する。

労基法34条の休憩（6時間超で45分、8時間超で60分）を
自動控除する実装は、**控除ルールが会社ごとに違う**うえ、
実態と違う控除をすると「実際は働いていたのに休憩扱いにされた」
という、未払い賃金そのものの争点を作る。
デモで踏み込む領域ではない。実導入時に会社ごとに決める。

#### 6.4.5 上限アラートは「注意喚起」であって判定ではない

36協定の上限（月45時間・年360時間、特別条項で月100時間未満・
複数月平均80時間）に接近したら管理画面で強調する。ただし

> **これは法令判定ではありません。実際の36協定の内容と
> 就業規則に基づいて社労士にご確認ください。**

を画面に常時表示する。**中小企業の36協定は内容が会社ごとに違い、
起算月も特別条項の有無も個別**なので、システムが「違反です」と
断定すると誤りになる。しきい値は管理画面で変更できるようにし、
既定値は法定の一般条項（月45時間）に置く。

| 表示 | 条件（既定値） |
|---|---|
| 通常 | 月の時間外が 30 時間未満 |
| **注意** | 30 時間以上 |
| **警告** | 45 時間以上 |

時間外＝法定労働時間（週40時間・日8時間）を超えた分。
デモでは**日8時間超**の単純計算とし、週40時間の判定は入れない。
変形労働時間制・みなし残業を持つ会社では計算が変わるため、
ここも「実導入時に会社ごとに決める」と明示する。

#### 6.4.6 CSV 出力

給与計算は既存の会計ソフト・社労士に渡す前提で、**このシステムで
給与は計算しない**。月次の CSV（本名・日別実働・時間外・打刻異常）を
総務・安全管理がダウンロードできれば足りる。

CSV には画面と同じ `users.name` を使う（→ 3章）。給与用途では管理者が正式名を設定する運用とし、別の表示名は持たない。

> **商談での見せ方**: 「打刻を集めるところまでは、どの勤怠アプリでもできます。
> **これは私物のスマホだけで、追加の機械を1台も買わずにそこまで行きます**」。
> 打刻端末が余っている PC 1台でよいこと（→ 6.3）とセットで話す。

### 6.5 申請（有給・各種届出を1機能に統合する）

**有給休暇も、直行直帰も、早退も、シフト希望も、すべて「申請」1機能で扱う。**
種別が違うだけで、**申請 → 承認 → 差戻し**という骨格は完全に同じ。

当初は「有給休暇」と「届出」を別機能として設計したが、統合した。
分けると**承認フローを2重に実装する**ことになり、片方だけ直して
食い違う事故が起きる。やること（→ 6.2）で権限判定をSQLの条件に
含めて一本化したのと同じ理由。

有給は「残日数を持つ種別」であって、別の機能ではない。

#### 6.5.1 種別はテーブルで持つ

```
request_types (code, label, unit, needs_balance, sort_order, active)
```

コードに分岐を書かず、**種別を足すのは行を1つ足すだけ**にする。
中小企業ほど「うちは慶弔休暇も申請させたい」が出てくるので、
ここを固定すると導入のたびにコード修正になる。

| code | 表示 | 単位 | 残数管理 |
|---|---|---|---|
| `paid_leave` | 有給休暇 | 日（0.5刻み） | **する** |
| `absence` | 欠勤 | 日 | しない |
| `direct` | 直行直帰 | 回 | しない |
| `early_leave` | 早退・遅刻 | 回 | しない |
| `shift` | シフト希望 | 回 | しない |
| `overtime` | 残業申請 | 回 | しない |

`needs_balance` が真の種別だけが残日数を消費する。
**分岐が要るのはこの1フラグだけ**で、あとは共通処理で流れる。

#### 6.5.2 状態遷移はやることと同じ形にする

```
申請(pending) ──承認──▶ 承認済(approved)
      │                        │
      ├──却下──▶ 却下(rejected)  └──取消──▶ 取消(cancelled)
      └──取下げ──▶ 取消(cancelled)
```

| 遷移 | 行える人 |
|---|---|
| （作成）→ 申請 | 本人。**打刻端末を除く全員** |
| 申請 → 承認済 | 代表・管理 |
| 申請 → 却下 | 代表・管理 |
| 申請 → 取消 | **本人**（承認前の取下げ） |
| 承認済 → 取消 | 代表・管理 |

**やること（→ 6.2）と同じく、条件付き UPDATE 1文**で
現在状態と実行者の資格を同時に判定する。D1 にトランザクションが
無いため（→ 12.2-9）、確認してから更新の2手には分けない。

**自分の申請を自分で承認できない。** SQL の条件に
`user_id <> ?actor` を含めて、総務・安全管理自身の有給申請も
別の管理者の承認を要する形にする。代表が1名しかいない会社では
代表の申請を総務・安全管理が承認する運用になるが、
**「誰も承認できない」状態を作らない**ために代表・管理は相互に承認できる。

#### 6.5.3 有給の残日数は「付与」と「消化」の差で出す

残日数のカラムを持たない。**付与行と消化行の差**として計算する。

```
leave_grants   (user_id, days, granted_on, expires_on, note)   -- 付与。年次・入社時
requests       (…, days)                                        -- 消化。承認済のみ数える
```

残日数カラムを持つと、**申請の取消・却下・打刻修正のたびに
加減算が要り、1回でも漏れると残日数が永久にずれる**。
しかも有給は**2年で時効消滅**（労基法115条）するため、
「いつ付与された分か」を持たないと時効の計算ができない。
付与行を残す形なら、時効は `expires_on` を見るだけで済む。

```sql
-- 残日数 = 有効な付与の合計 − 承認済みの消化の合計
select
  coalesce((select sum(days) from leave_grants
             where user_id = ?1 and expires_on >= ?2), 0)
  -
  coalesce((select sum(r.days) from requests r
             where r.user_id = ?1 and r.type_code = 'paid_leave'
               and r.status = 'approved'), 0) as remaining
```

**消化は古い付与から充てる（先入先出）**のが実務の原則だが、
デモでは残日数の合計だけを出し、付与単位の内訳は持たない。
時効が絡む厳密な引き当ては実導入時に詰める。

#### 6.5.4 年5日の取得義務を管理画面で可視化する

2019年4月から、**年10日以上付与される労働者には年5日の取得が義務**で、
**違反は労働者1人あたり30万円以下の罰金**。
「取得させていない」ことに気づいていない中小企業が実在する。

管理画面に、対象者ごとの取得日数と残り必要日数を一覧で出す。

```
田中（付与 20日 / 基準日 2026-04-01）   取得 1日  ← あと4日  ⚠
佐藤（付与 12日 / 基準日 2026-04-01）   取得 6日  ✓
```

これは**6機能のなかで最も「知らなかった」と言われる可能性が高い**画面で、
商談で刺さる。ただし 6.4 と同じく判定ではなく注意喚起として出し、
社労士確認を促す文言を添える。

#### 6.5.5 残数の検証は申請時と承認時の両方で行う

申請時に残数が足りていても、**承認までの間に別の申請が承認されて
足りなくなる**ことがある。D1 にトランザクションが無いため、
承認の UPDATE 実行時にもう一度残数を確認する。

ここは条件付き UPDATE 1文に畳めない（残数が集計値のため）ので、
**承認後に残数が負になっていないかを確認し、負なら承認を取り消す**
補償方式にする。19名規模で同時承認が競合する確率は無視できるが、
**負の残数が表示される**ことだけは防ぐ。

#### 6.5.6 申請はれんらくに流さない

「申請が出たことを管理者に知らせたい」が必ず出るが、
**れんらくへの自動投稿はしない**。通知を実装しない方針（→ 6.1）と同じく、
**一覧の60秒部分更新**で未承認件数バッジをヘッダーに反映する（`hx-swap-oob`）。

自動投稿すると、れんらくが機械的なメッセージで埋まり、
**人が判断を残す場所という6.1の性格が壊れる**。

### 6.6 点検（チェックリスト）

**テンプレートを定義し、日次でインスタンス化して現場が埋める。**
開店前点検、清掃、車両点検、機器点検、飲食店の HACCP 温度記録。

飲食店は**2021年6月から HACCP に沿った衛生管理が義務化**されており、
記録簿の作成・保存が要る。いまも紙のバインダーが現役で、
**書き忘れても後から遡って書ける**（＝証跡として弱い）状態にある。

このシステムで記録すれば、**誰がいつ記録したかがサーバ時刻で残り、
後から書き換えられない**。打刻（→ 6.3）で時刻の出所を1箇所に
確定させたのと同じ考え方が、そのまま記録の信頼性になる。

#### 6.6.1 3階層で持つ

```
checklists        テンプレート  「開店前点検」
  └ checklist_items  項目       「冷蔵庫の温度」「床の清掃」
checklist_runs    実施1回分     「2026-08-01 の開店前点検」
  └ checklist_results 結果      項目ごとの ✓／数値／コメント
```

**テンプレートを複製して実施記録を作る形にはしない。**
項目を後から直したときに過去の記録まで変わると証跡にならず、
かといって複製すると項目マスタとの対応が切れる。
`checklist_results` が `checklist_item_id` を参照し、
**項目行は論理削除（`active = 0`）にして物理削除しない**。

#### 6.6.2 入力の型は3つだけ

| 型 | 用途 | 保存 |
|---|---|---|
| `check` | ✓/✗ | `value_bool` |
| `number` | 温度・数量 | `value_number` ＋ 範囲逸脱の警告 |
| `text` | 備考 | `value_text` |

写真は持たない。添付BLOB（→ 2.4）は1MB上限で、
**点検が毎日全項目で写真を撮ると D1 の 5GB を現実的に食う**。
写真付き記録は R2 前提の実導入時に足す。

`number` には `warn_min` / `warn_max` を持たせ、
**範囲外なら警告表示するが、保存は拒否しない**。
冷蔵庫が実際に 12℃ なら、それは記録すべき事実であって
入力エラーではない。**弾くと「入るまで嘘の数字を入れる」**という、
記録簿として最悪の運用を誘発する。

#### 6.6.3 実施日は「1テンプレート1日1回」に固定する

`checklist_runs` に `(checklist_id, run_date)` の UNIQUE 制約を置く。
同じ点検が1日に2つできると、どちらが正か決められない。
1日2回の点検（開店前・閉店後）が要るなら、
**テンプレートを2つ作る**のが正しいモデル化になる。

#### 6.6.4 未実施の可視化が本体

チェックリストの価値は「埋まった記録」ではなく
**「埋まっていないことが見える」**ことにある。
管理画面に、テンプレート×直近7日のマトリクスを出す。

```
             7/26 7/27 7/28 7/29 7/30 7/31 8/1
開店前点検     ✓    ✓    ✓    —    ✓    ✓    ✓     ← 7/29 未実施
車両点検       ✓    ✓    ✓    ✓    ✓    ✓    —
```

### 6.7 現場

現場そのものの持ち方（進行状態・種別・問題発生）と、**現場の担当者に閉じた
確認型スレッド＝現場れんらく**を扱う。見える範囲は `place_members` が決める。

#### 6.7.1 現場れんらくはれんらくと同じテーブルで扱う

**れんらくと現場れんらくは同じテーブルで扱う**（→ 6.1）。やることが
`related_type` で社内・営業・現場・集金を1つで扱えているのに、れんらくだけ
現場を別テーブルへ切り出す理由がない。分けていた頃は未読の判定・回答の記録・
取り下げまで二重に実装され、片方だけ直す事故が起きていた。

`messages.related_type` は `internal` / `sales` / `place` / `collection` の4種で、
`related_id` がその対象を指す。既存のれんらくは `internal` になる。
回答必須の持ち方は**指名（`message_mentions`）に揃えた**。現場れんらくの
「見る人全員が回答」は、宛先全員を指名へ展開して表す。

現場れんらくは宛先が担当者で自動的に決まるので、DM 禁止の3名以上制限は外す。
あの規則は「宛先を自分で選ぶ」れんらくのためのもので、2名の現場でも
連絡できる必要がある。

れんらく一覧（`/renraku`）は社内の連絡だけを並べる。現場・営業・集金の連絡は
それぞれの詳細画面に読む場所があり、一覧に混ざると「どこの話か」を毎行たどる
ことになる。ホームだけは混ぜる（そこは今日やることを1か所に集める場所）。


**現場詳細の「申し送り」は「れんらく」へ統一し、その現場の担当者だけを
自動的に見る人とする。**

夜勤から朝番への引き継ぎ、店舗の連絡帳、現場ごとのメモ。
通常のれんらく（→ 6.1）と同じく、回答不要なら未読・既読、回答を求める場合は
未回答・OK・NGと20文字以内の任意返信を扱う。宛先選択は置かず、発信時点の
`place_members` を見る人として固定する。これにより担当変更後も、誰に届けた
れんらくかと当時の応答記録が変わらない。

#### 6.7.2 ホームの「れんらく」に混ぜる

現場れんらくは**ホームの「れんらく」へチームれんらくと混ぜて出す**。
現場ごとに詳細を開かないと気付けないのでは、現場を多く持つ人ほど見落とす。
1つの一覧に混ぜ、新しい順に並べる。どの現場かはカード本文の先頭に
`【現場名】` として出す。

ホームに出すのは**未読と未回答だけ**。ホームのれんらくは「今対応するもの」を
並べる場所なので、読み終えたものは残さない（現場詳細は当日まで残す）。

ヘッダーの未読件数にも含める。一覧に出るのに件数へ入らないと
「0 件なのに未読がある」状態になる。

れんらく一覧（`/renraku`）はチームれんらく専用のまま変えない。
そこは「チームで確認と回答を共有する場所」で、現場ごとの連絡とは別の話題。

#### 6.7.3 読み終えた連絡は翌日から消える

現場詳細は「今この現場で対応することを見る場所」なので、片付いた連絡を
積み上げない。**未読と未回答は日付に関係なく残し、既読になったものは
その日のうちだけ残して翌日から消す**。読んだ直後に消えると
「さっき見たものがもう無い」となって混乱するため、当日は残す。

判定は日本時間の当日で行う。UTC のままだと朝9時までが前日扱いになる。

消えた連絡は見出し右の「すべて見る」（`?handovers=all`）から辿れる。
現場の経緯は残す必要があるので、消すのは表示だけでデータは触らない。

カード左の線は**まだ対応が要る印**とし、未読か未回答のときだけ出す。
既読で回答も済んだものからは消す。全部に付いていると印にならない。
線のぶんの幅は常に確保し、読んだ瞬間に文字がずれないようにする。

#### 6.7.4 現場の進行状態と種別

現場の進行状態は **準備中・施工中・完了** の3段階とし、今日と現場一覧の
カード左上へ表示する。新規現場は準備中、営業から転記した現場も準備中で開始し、
状態を変更した日時と変更者は変更履歴へ残す。

現場は **単発・継続** の2タイプを持つ。既存現場は単発として扱い、継続は点検・清掃など
同じ場所で期間中に繰り返す仕事に使う。継続現場には作業種別、開始日、終了日、
繰り返し条件を必須で持たせる。毎週の複数曜日、毎月の特定日、祝日の振替、休止期間など
条件を複合できるよう、繰り返し条件は400文字以内の文章で記録する。

継続現場そのものは契約と予定を表し、個々の実施回は「やること」として作業者へ割り当てる。
作業者は入退場を記録し、完了時の必須コメントを実施報告として残す。将来、予定から実施回を
自動生成する場合も、この現場とやることの分離は維持する。

#### 6.7.5 問題発生は進行状態とは別に持つ

**問題発生は進行状態とは別に持つ。** 商談中・施工中・請求中などの現在地を
失わずに警告を付け、問題が解消したら警告だけを外せるようにする。問題発生中は
赤色のステータスだけを強調し、概要は通常の文字色で表示する。今日画面に問題専用枠は
作らず、営業・現場・集金それぞれの先頭へ問題のカードを表示する。今日画面のカードには
共有範囲と現場住所を表示せず、判断に必要な問題概要と担当者へ絞る。
協力会社員には従来どおり担当現場の問題だけを表示し、営業・集金の詳細権限は広げない。
問題発生を選ぶときは「問題の概要と最新状況」を必須とし、詳細画面へ常に表示する。
内容を更新するたびに変更前後・変更者・変更日時を変更履歴へ記録し、問題と対応状況が担当外にも伝わるようにする。
変更履歴は担当者IDの集合で比較して並び順だけの差を記録せず、テキストは削除・置換された文字を赤色の取り消し線、追加された文字を緑色で表示する。
今日画面への共有範囲は **担当者・関係社員・全社員** から選ぶ。担当者を初期値とし、
関係社員は同じ営業・現場・集金に紐づく担当者まで、全社員は重大問題に限って使う。
直接の担当者には共有範囲にかかわらず必ず表示し、協力会社は担当現場だけに限定する。

#### 6.7.6 画面もれんらくと共通にする

**テーブルだけでなく、画面も1組にする。** 作成・変更・詳細・回答のすべてを
`/renraku/...` で扱い、現場れんらく専用の画面は持たない。

当初は「認可条件と作成画面が異なる」ことを理由に `handovers` 系の専用テーブルへ
分けていたが、0043 で `messages` へ統合した（→ 6.1）。にもかかわらず**画面だけ
2組のまま**残していたため、回答を5択にする改修で同じ変更を2箇所へ書くことになり、
**片方（現場側）に入力欄を書き忘れる**という、統合が防ぐはずだった事故が実際に起きた。

違いとして残るのは次の2点だけで、いずれも `related_type` で分岐すれば足りる。

- **見る人の決まり方** — 現場は `place_members` から自動解決する（宛先を選ばせない）
- **戻り先と見出し** — 現場れんらくは現場詳細へ戻り、現場名を添える

```
places   (id, name, stage, has_issue, issue_summary, issue_scope, active, address, latitude, longitude,
          surrounding_notes, site_notes, estimated_effort,
          work_period, contact_info,
          place_type, service_type, start_date, end_date, recurrence_rule)
messages (id, author_id, body, scope, created_at, withdrawn_at, withdrawn_by,
          related_type, related_id, answer_options)   -- related_type='place' が現場れんらく
```

古い URL（`/places/:id/renraku/...`）は統合先へ転送する。GET は 301、
POST は**メソッドを保つ 307** を使う（303 だと本文が消えて回答が失われる）。

#### 6.7.7 見える範囲は「場所への割当」で決まる

```
place_members (place_id, user_id)
```

代表・総務・現場監督・自社技術者の**社員は全現場**を見られる。
協力会社員は**`place_members` に行がある担当現場**に限定し、
れんらく・やることと同じく**EXISTS が絞り込みを担う**。
発信時点の見る人に含まれない現場れんらくを URL で直接開いても、
存在しない ID と同じ 404 を返す。

`place_members` は社員に対する閲覧許可ではなく、その現場の担当者表示に使う。
社員の異動や応援で一覧が欠けないよう、社員の閲覧範囲はロールで全現場に固定する。
今日画面と現場一覧の担当表示は営業・集金と同じ形式にし、実務担当者を列記して、
管理担当者は右側へ小さな括弧付きで表示する。

現場詳細は、現場名の後を **れんらく → やること → 変更履歴（履歴がある場合だけ）→
担当 → 現場情報** の順にする。未完了件数・担当・れんらく件数の集計パネルは置かず、
現場で先に確認するれんらくと作業を上へ集める。

協力会社が複数の現場を渡り歩く場合、管理者が割当を足し外しする。
発信後に担当から外れても発信時点で受け取った現場れんらくは残るが、現場自体を
閲覧できない協力会社には一覧から現場を見せない。
BYOD の文脈では、これは「端末に残らない」と同じ方向の価値になる。

#### 6.7.8 協力会社と協力会社員

**会社は利用者ではない。** `partner_companies` だけが会社を表し、`users` の行は必ず人。
「契約主体としての協力会社ユーザー」は廃止した。会社と人が同じ表に混在すると、
名簿に会社名のような人が並び、どちらを指しているのか読めなくなる。

協力会社の人は `role = 'contractor'` の**協力会社員だけ**とし、社員／パートの区別は持たない。
一度は `partner_worker_type` で分けたが、**それは協力会社側の雇用形態であって、
発注者が把握・区別する立場にない。** 持っていること自体が「相手の雇用へ踏み込んでいる」
外観を作り、請負として説明しづらくなる（→ 下記の指揮命令の節）。

所属は `users.partner_company_master_id` が会社マスタへ接続し、
会社名や記号を変えれば所属者全員の表示が同時に変わる。

**会社ごとの停止は `partner_companies.status` が担う。** 停止した瞬間、
その会社に所属する全員が `resolveSession` で弾かれる（契約終了を1操作で表す → 9章 台本4）。
協力会社員には、全社のれんらく・給与用の労働時間集計・営業・集金を見せない。

#### 6.7.9 入退場の記録と指揮命令の境界

協力会社員の入退場を記録するのは、**元請の安全衛生上の義務の履行**であって
指揮命令ではない（安衛法29条の指導義務、30条の作業間の連絡調整・統括管理）。
建設業では作業員名簿・入退場記録は法定書類に近い扱いになる。

危ないのは、その記録が**労働時間の管理に見えてしまう**場合。
請負と認められるには、受注者が自ら始業終業・休憩・休日の指示や労働時間の管理、
業務遂行方法の指示、服務規律の決定を行っている必要がある（37号告示の区分基準）。

| これはよい | これは危ない |
|---|---|
| 現場にいたかを記録する（安全管理） | 遅刻・早退を本人に注意する |
| 入退場の時刻を残す | 「何時に来い」と本人へ直接指示する |
| 会社単位で稼働状況を把握する | 個人の残業時間を集計・管理する |
| 会社の主担当へ連絡する | 個人へ直接作業内容を指示する |

**この設計はそれを構造で守っている。**

- 画面用語を「出勤/退勤」ではなく**「入場/退場」**にする（雇用ではなく現場への出入り）
- 協力会社員を**給与用の労働時間集計から外す**（`role <> 'contractor'`）
- 是正の宛先として会社マスタに**主担当**を持たせ、個人ではなく会社へ連絡する
- 停止の単位を**個人ではなく会社**（＝契約）に置く
- 名簿に「安全管理のための記録であり労働時間の管理ではない」と明記する

なお実際の契約形態での適法性判断は社労士・弁護士の領域であり、
ここに書いたのは**画面と用語をどちら側に寄せるか**という設計判断である。

#### 6.7.10 応答状況の扱い

回答不要では未読・既読、回答を求める場合は未回答・OK・NGを表示する。
応答状況を見られるのは通常のれんらくと同じく、発信者・代表・管理とする。
本文と回答方針は変更でき、変更履歴を参加者へ表示する。取り下げたれんらくは
現場詳細の一覧から外すが、本文と履歴は削除しない。

### 6.8 文書（読み取り専用の共有棚）

就業規則、価格表、作業手順、安全マニュアル、緊急連絡先。
**紙か、LINE のアルバムか、社長の頭の中**にしかない会社が多い。

6機能のなかで**実装が最も軽く**、かつ
**本設計の既存の作り込みがそのまま機能価値になる**。

| 既にあるもの | 文書機能での意味 |
|---|---|
| `Cache-Control: no-store`（→ 4章） | **端末に保存されない社内資料** |
| 添付の閲覧を監査ログに記録（→ 7章） | 誰がいつ就業規則を見たか残る |
| 稼働/停止（→ 3章） | 退職者はその瞬間から読めない |
| ワンタイムトークン配信（→ 4章） | URL を転送しても他人は開けない |

#### 6.8.1 本文はテキストで持ち、PDF は添付として扱う

```
documents      (id, title, body, category, updated_by, updated_at, active)
document_files (id, document_id, blob, mime, bytes, created_at)  -- 1MB上限
```

本文を Markdown ではなく**プレーンテキスト＋改行**で持つ。
Markdown レンダラを入れると、CSP（`default-src 'none'`）の下で
**HTML を組み立てる経路が増え、XSS の面が広がる**。
就業規則に装飾は要らない。

PDF は `document_files` に置くが、**1MB 上限は文書には厳しい**。
就業規則の PDF は数MB になることが普通なので、
**デモではテキスト本文のみを扱い、PDF 添付は実導入（R2）で足す**と
明示する。ここを曖昧にすると商談で「PDFは置けますか」に詰まる。

#### 6.8.2 編集は代表・管理のみ、閲覧は全員（打刻端末を除く）

`terminal` ロールは業務データを一切表示しない（→ 1章）ため、
文書も見えない。ここは他機能と同じ扱いでよい。

**版管理は持たない。** 更新者と更新時刻だけを残す。
就業規則の版管理が要る規模なら、それは文書管理システムの領域で、
BYOD のデモが担う範囲を超える。

#### 6.8.3 閲覧の監査は「開いた瞬間」に記録する

一覧は記録しない（→ 7章の方針どおり、60秒部分更新が
記録を生成し続けるため）。**本文を開いた1回だけ**を記録する。

> **商談での見せ方**: 「就業規則、いま従業員はどこで見られますか」と振る。
> 多くは「事務所の棚」か「配ったきり」。**「スマホで読めて、
> しかも端末には残らず、誰が読んだか記録が残ります」**まで一息で言える。

### 6.9 今日のサマリー（ホーム先頭の一言）

ホームの先頭に、その人の今日の状況を1〜2文で出す。れんらく・やること・現場・
集金を横断して「まず何をすべきか」を示す。各機能を順に開かなくても、
朝いちばんに全体が掴める状態にするのが目的。

**前回の生成から60分経つまでは作り直さない。** 結果は
`daily_summaries` に利用者1人1行で置き、`created_at` からの経過で
判定する。毎回生成すると表示のたびに数秒待たされ、費用も
人数×表示回数になる。一方で1日1回だと、午前に見た内容が夕方まで残り
「今の状況」として読めない。

**区切りを時計の正時にしない。** 正時だと 9:59 に作った文が 10:00 に
作り直され、**1分で更新**されてしまう。「1時間ごと」と説明したときの
動きと合わない。経過時間で見れば、いつ開いても前回から60分は保たれる。

費用は1人あたり1日最大24回。実測 0.091円/回なので、19名で月100円弱
（→ 課金試算）。

**表示はホームの読み込みを待たせない。** 生成に数秒かかることがあるため、
ページを返したあとに htmx で差し込む。失敗したときは**何も出さない** —
サマリーはあると助かるものであって、無いと困るものではない。

#### 6.9.1 件数ではなく内容を送る（実装時の決定）

当初は件数だけを送っていた（「未回答のれんらく: 2件」）。
これをやめ、**れんらくの本文・やることのタイトル・現場の申し送りまで
渡して、総合して判断させる**ようにした。

件数だけでは、AI は**並べ替えることしかできない**。「未回答2件」が
急ぐのか放っておけるのかは本文を読まないと決められず、
「期限切れが1件あります」以上のことが言えない。内容が入って初めて
「どれから手を付けるか」を選べる。ここがこの機能の価値になる。

材料は見出しを付けて渡す。本文が混ざるため、**どこからどこまでが
何なのか**が読めないと、現場メモとれんらくを取り違える。

```
【出勤打刻】済み

【れんらく】
- [要回答] U1より: 西町スーパーの夜間作業は22時15分入場です。脚立の識別票と…
- [未読] U3より: U4さんに鍵を借りてから入場してください

【やること】
- [期限切れ] 冷媒配管の耐圧試験（P2）

【担当している現場】
- P2: 問題あり: 室外機の設置場所が図面と違い、C2の担当者と再調整中、未完了の作業3件

【今いる現場（P2）の申し送り】
現場での注意: 反射ベスト必須。5番ゲートから入場し、U4に声かけ
```

#### 6.9.2 れんらく・やることに関連先を添える（実装時の決定）

れんらくとやることには、それがどの現場・案件の話かを併記する。

```
【れんらく】
- [要回答] U1より（P2）: 西町スーパーの夜間作業は22時15分入場です…

【やること】
- [期限切れ] 冷媒配管の耐圧試験（P2）

【担当している現場】
- P2: 問題あり: 室外機の設置場所が図面と違い…
```

**記号が揃うことに意味がある。** 「P2 の作業が期限切れ」と
「P2 で問題が出ている」が同じ記号で書かれていれば、AI は
両者を同じ現場の話として繋げて読める。記号が無いと、
れんらく・やること・現場が互いに無関係な3つの列に見える。

#### 6.9.3 案件タイトルは辞書に入れない

営業案件のタイトルは「青葉食品工場 空調更新 第1回」のように
**現場名を含む**。これを伏せ字の辞書へ入れると、長い名前を優先する
`maskText` がタイトル全体を `S1` に置き換え、**中の現場名が消える**。
`S1` と `P2` が同じ現場だと分からなくなり、関連先を渡した意味がなくなる。

辞書に入れるのは現場・取引先・人だけにする。タイトルは
「P2 空調更新 第1回」の形で伏せられ、現場との対応が残る。

ただしこれだけでは足りない。案件タイトルの頭は
**取引先名の略称**のことがある（タイトル「若葉ホテル 客室空調改修」に対し、
登録名は「若葉ホテル株式会社」）。辞書は完全一致で置換するため当たらず、
社名が素通りする。

そこで、**伏せ字が1つも入らなかった関連先だけ**、タイトル全体を
`S1` へ置き換える。現場名が当たったものは `P2` のまま残るので、
繋がりを保ったまま、繋がりを持たない案件の社名も漏れない。

#### 6.9.4 打刻には触れない（実装時の決定）

**サマリーは打刻を材料にしない。** 出勤時刻も、場所も、
「まだ打刻がありません」も送らず、文にも出さない。

当初は出勤打刻の時刻と場所まで渡し、まだ打刻が無いときだけ
やんわり促していた。これをやめた理由は**更新頻度**にある。

サマリーは前回の生成から60分は作り直さない（→ 6.9）。
そのため「出勤の打刻がまだのようです」は、**打刻を済ませたあとも
最大1時間そのまま出続ける**。利用者から見ると、済ませた用事の
指摘が消えない。消す手段が無い指摘は、読み飛ばす癖を作るだけで、
その下に並ぶ本当の要点まで一緒に読まれなくなる。

打刻の状態は**ホームの現在状態バッジがすでに常時示している**（→ 6.1）。
こちらは打刻した瞬間に変わるので、催促の役目はそちらで足りている。
同じことを、遅れて更新される場所で二重に言う価値がない。

材料から外すと、外へ送る内容から**時刻と場所が丸ごと消える**副次効果もある。
伏せ字を通していたとはいえ、送らずに済むものは送らないほうが良い（→ 6.9.6）。

**AI 側には名指しで禁じる。** 「打刻」は材料に無くても書けてしまう
一般論なので、「材料に無いことを書かない」だけでは足りない。
`- **出退勤や打刻のことは書かない**` を守ることに入れる。

> **勤務中かの判定は別**（→ 6.9.15）。退勤したらホームから業務情報を
> 消す判定は打刻を見ているが、これは**サマリーを出すかどうか**の話で、
> サマリーの中身とは関係ない。

#### 6.9.5 申し送りを取り込み、パネルは1つにする

入場した現場のメモ（→ 6.10）を、サマリー側の材料に渡す。
現場の注意事項を見ずに「今日いちばん効くこと」は選べない。

当初は画面のパネルを2つのまま残した（サマリーと申し送り）。
これは誤りで、**同じ注意が2箇所に出る**。サマリーが現場メモを読んで
要約に含める以上、申し送りパネルは同じ内容の繰り返しにしかならない。

申し送り専用の生成（`generateArrival` / 専用プロンプト / `/today/arrival`）
は削除した。`arrival.ts` に残すのは**材料集めだけ**で、文にするのは
サマリー側。伏せ字も送信も一箇所に集まり、外部送信の経路も1つになる。

安全の注意が埋もれないよう、材料は独立した見出しで渡し、
指示にも「現場の申し送りがあるときは、安全に関わる内容を優先して拾う」
と書いている。

#### 6.9.6 伏せ字は「名前」にかかる。内容にはかからない

生成に Claude API を使う。ここが本設計で唯一、業務データが
**Cloudflare の外へ出る**経路になるため、名前を置き換える。

- **氏名・現場名・取引先名を、その回限りの連番へ置き換える**
  （`P1`=現場 / `C1`=取引先 / `S1`=案件 / `U1`=人）
- 置き換えは**自由記述の中にも及ぶ**。「岩瀬 健太さんに鍵を借りる」は
  「U4さんに鍵を借りる」になる
- 返ってきた文の伏せ字を、画面へ返す直前に実名へ戻す
- **対応表は生成処理の中だけに存在し、保存も記録もしない**

そのために、**本文に登場するかに関わらず名簿全体を先に辞書へ入れる**。
対応表に無い名前は置換できないので、「その名前が出てきたら伏せる」
という作りにはできない。

ID をそのまま伏せ字に使う案は採らない。`demo_place_factory` のように
**人が付けた ID から業種が読める**ことがあり、ID の命名規則に
安全性を依存させたくないため。

> **重要な限界**: 伏せ字が効くのは**登録済みの名前だけ**。
> れんらくに書かれた「西町スーパーの夜間作業は」の社外の会社名や、
> 取引先の担当者名は辞書に無く、**そのまま送信される**。
> 「例の件、社長には言わないで」のような文脈依存の情報も消せない。
>
> したがって、**「名前は一切送りません」とは言えなくなった**。
> 言えるのは「登録済みの氏名・現場名・取引先名は記号に置き換えます」まで。
> 確認画面（→ 下記）で人が読む工程を残しているのはこのため。

#### 6.9.7 挨拶を添えて、急かさない

パネル名は**「AIサポート」**。文は時間帯に合う挨拶（おはようございます /
お疲れ様です）で始め、やわらかい言い回しで書く。

- 「〜してください」ではなく「〜すると良さそうです」
- 期限を過ぎていても**responsibility を問わない**。事実と次の一歩だけ
- 材料を全部並べず、今いちばん効くものに絞る

急かす文面にしないのは、**私物端末に出る通知だから**。BYOD では
業務時間外にも同じ画面を開く。強い言葉で残ると、端末を開くこと自体が
負担になる。ルールベース側の文も同じ調子で書く。

#### 6.9.8 挨拶＋要点だけを短い一段落で出す（実装時の決定）

内容を送るようにしたことで詳しい案内も作れるが、ホームの先頭で長文を出すと
れんらくややることへ進みにくい。詳細は各機能で確認できるため、サマリーは
**通常は要点を1件だけ、重要なものが複数ある場合だけ最大2件を、
改行なし・120文字以内**で出す。

複数を出す場合は、安全性・期限・影響範囲を基に参考となる順で並べる。
ただし「まず」「次に」「最優先」など着手順を強制する言葉は使わない。
番頭が順番を決めるのではなく、現場の状況を知る本人の判断に委ねる。

```
おはようございます。青葉食品工場の問題対応と、現場注意の確認が今日のポイントです。
```

`daily_summaries.body` の上限は600文字のままにする（→ migration 0050）。
生成指示の120文字を少し超えても、保存時に文を途中で切らないための余裕である。

`stop_reason` が `max_tokens` で返ったときは、途中で切れた文を見せず
ルールベースの完結した文へ落とす。

#### 6.9.9 行数を固定すると、AI は事実を作る（実装時の決定）

当初は「箇条書きを2〜4行」と指示していた。これが**捏造の原因**になった。

材料が申し送り1件しか無い協力会社の画面に、次の文が出た。

```
・sumpoからの要回答連絡に、自社技術者と協力会社へ回答する必要があります
・明日朝礼が7時50分開始のため、事前に資料を確認しておくと安心です
```

**送った材料は出勤打刻と現場メモの4行だけ**で、れんらくも やること も
0件だった。「朝礼7時50分」はどこにも存在しない。
れんらく欄・やること欄が「ありません」と表示されている画面の上で、
AI だけが対応の必要を語っていた。

原因は行数の指示そのもの。「2〜4行」は材料の量に関わらず
**下限として働き**、埋めるために事実が作られる。
「材料に書かれていないことを書かない」という禁止だけでは足りなかった。

対処は2つ。

- **通常は要点を1件に絞り、重要なものが複数ある場合だけ最大2件にする。**
  下限は設けず、材料が無ければ要点を書かない
- **何を作ってはいけないかを名指しする。** 「時刻・日付・予定を
  自分で作らない。朝礼、開始時刻、締切、来訪予定は材料にあるものだけ」

> **この機能の限界**: 生成物である以上、事実に無いことが混ざる
> 可能性は残る。**サマリーは業務の一次情報ではない**という位置づけを
> 崩さない（れんらく・やること・現場の各画面が正）。
> 表示は「あると助かるもの」に留め、ここだけを見て動く設計にはしない。

#### 6.9.10 見出しを置かず、吹き出しで出す（実装時の決定）

**「AIサポート」という見出しは置かない。** その4文字は読む人の役に立たず、
**1行ぶん本文が下へ遠ざかる**だけになる。ホームの先頭で最初に読ませたいのは
今日の状況であって、機能の名前ではない。

パネルの形は**吹き出し**にする。れんらく・やることのカードは
「白地＋枠＋左の縦線」で並ぶので、同じ形にすると一覧の続きに見え、
**相棒からの一言という性格が伝わらない**。丸いアイコンと吹き出しなら、
横に並べても別のものだと分かる。

#### 6.9.11 「番頭」の色で AI 製かどうかを示す

丸い「番頭」表示の色を2種類使い分ける。

| | 表示 | 意味 |
|---|---|---|
| AI が書いた | `番頭`（アクセント色） | 内容を読んで優先順位をつけた文 |
| ルールベース | `番頭`（灰色） | 決め打ちの順で並べただけの文 |

同じ場所に同じ形で文が出る以上（→「AI が無くても成立させる」）、
**どちらを読んでいるのか区別できないと、質の違いに気づけない**。
停止中・キー未設定・生成失敗のいずれでも灰色になる。

判定は `daily_summaries.used_ai` に保存する（→ migration 0051）。
保存しないと、60分の使い回しの間だけ**本文は AI 製なのに番頭表示は灰色**
という食い違いが起きる。

#### 6.9.12 AI が無くても成立させる

**API キーが未設定でも、生成に失敗しても、同じ場所に文が出る。**
件数はすべて確定した事実なので、文章にするだけなら AI は要らない
（`ruleBasedSummary`）。AI を使うのは、集金の期限と現場の完了報告の
関係のような、**組み合わせで意味が変わる部分**の言い回しのため。

この作りにより、
- 商談で「AI 抜きでも動きます」と実演できる
- Claude API が落ちてもホームは壊れない
- 「月0円で収まる」構成を、AI を切れば維持できる

> **未決**: 実導入では、この機能だけ外部送信が発生することを利用規約と
> 個人情報の取扱いに明記する必要がある（→ 12章）。顧客によっては
> **AI を切って運用する**選択肢を残すため、キー未設定で成立させている。

#### 6.9.13 送信内容は人が確認してから送る（実装時の決定）

外部送信が起きる唯一の経路なので、**何を送っているかを画面で読める**
ようにする。`/admin/ai-debug` に、その人の今この瞬間の内容を4段で出す。

| 段 | 内容 | 実名 |
|---|---|---|
| 1 | 材料（集計した生データ） | **含む** |
| 2 | AI への指示（システムプロンプト） | 含まない |
| 3 | **実際に送信する本文**（伏せ字済み） | 含まない |
| 4 | 伏せ字と実名の対応表 | **含む** |

1段目を実名で見せるのは、**情報の過不足を判断するため**。「未完了3件」
だけでは多いか少ないか決められないが、現場名が分かれば妥当性が判断できる。
2段目は指示そのものが適切かを読むため。3段目が外へ出る文字列で、
ここに実名が残っていないことを目で確かめる。

**確認画面は本番と同じ関数を呼ぶ。** `collectSummaryFacts` →
`maskFacts` → `buildSummaryPrompt` の並びは生成側と共通で、
確認画面は途中の値を表示するだけ。別に組み立てると「確認した内容」と
「実際に送る内容」がズレて、確認そのものが無意味になる。

権限は監査ログと同じ（代表・管理）。1段目と4段目は実名を含むため、
**保存も監査記録もしない** — その場で作って返すだけにする。

#### 6.9.14 一時停止スイッチを持つ（実装時の決定）

`AI_SUPPORT=off` の間は**Claude API を呼ばない**。API キーは設定した
まま外部送信だけを止められる。

キーを外す運用と分けたのは、**「意図して止めている」と「キーの設定漏れ」が
区別できない**ため。どちらもフォールバックで同じ文が出るので、画面からは
見分けがつかない。確認画面の先頭に稼働／停止を出し、
**止めたつもりで動いていた**状態に気づけるようにする。

停止中もサマリーと申し送りは同じ場所に出る（ルールベース側）。
これは「AI が無くても成立させる」の作りをそのまま使っている。

#### 6.9.15 勤務中でなければ業務情報を出さない

**退勤したら、ホームから業務情報を消して「お疲れ様でした」だけにする。**
サマリー・れんらく・やること・営業・現場・集金のすべてが対象。

退勤したあとのホームに未読件数や期限が並んでいると、画面を閉じるまで
仕事が終わらない。BYOD は**私物端末**なので、業務時間外にも同じ端末を
生活で使う。**打刻で業務が切れる**ことを画面でも示す。

判定は「その日の最後の打刻が出勤か」。データが消えるわけではなく、
出勤すればまた出る。日付が変われば前日の出勤は引き継がれない
（打刻の取得が当日分に限られているため → 6.3）。

**代表・工事責任者と総務・安全管理は、自分の打刻と関係なく常に表示する。**
この2つの役割は全員の打刻を見て承認する立場（→ 1章のロール表）で、
自分が打刻していないことと、業務情報を見る必要があることが結びつかない。

| 役割 | 出勤中 | 退勤済・未打刻 |
|---|---|---|
| 代表・工事責任者 / 総務・安全管理 | 表示 | **表示** |
| 営業・現場監督 / 自社技術者 / 協力会社員 | 表示 | お疲れ様でした |

> **商談での見せ方**: 退勤を押した瞬間に画面が「お疲れ様でした」だけになる。
> **「私物のスマホに仕事が残り続けない」**が、言葉ではなく動作で伝わる。

#### 6.9.16 音声対応は検討事項を先に示す

番頭の吹き出しとれんらくの間に、受話器アイコン付きの
「番頭さんと通話する」を置く。
この段階では実際の通話を開始せず、音声対応に伴う追加料金と
AIへ渡す情報の保護を検討する必要があることをポップアップで説明する。

会社名や個人名などの固有名詞は、ランダム記号へ置き換えることで
AIへそのまま渡さずに処理できることも示す。商談では機能の可能性だけでなく、
費用と情報セキュリティを先に説明する姿勢そのものを訴求する。

### 6.10 入場時の申し送り

**現場で入場を打刻した直後に、その現場の注意事項だけを短く出す。**

現場メモ・周辺メモ・問題・未完了の作業は現場詳細に溜まっているが、
**開かないと見えない**。「食品区画は帽子・マスク必須」「診療中は騒音作業
不可」といった安全と段取りの情報は、読まれないと事故になる。打刻という
**必ず通る操作**の直後に、今日その人に関係するぶんだけ届ける。

材料は現場に既にあるものだけで、新しい入力欄は増やさない。

| 材料 | 出どころ |
|---|---|
| 現場での注意 | `places.site_notes` |
| 周辺・入退場の注意 | `places.surrounding_notes` |
| 発生中の問題 | `places.has_issue` / `issue_summary` |
| その人の未完了の作業 | `tasks` ∩ `task_assignees` |

#### 6.10.1 出す条件を絞る

次のすべてを満たすときだけ出す。ひとつでも欠ければ**何も表示しない**。

- 今日の直近の打刻が**入場**である（退場後・未打刻は出さない）
- その打刻に**現場**が紐づいている（事務所打刻では出さない）
- **その現場の担当者である**（`place_members` の JOIN が範囲を決める → 6.1）
- 書ける材料がひとつ以上ある

3つ目が要点で、**担当していない現場に入場しても中身は見えない**。
打刻の場所は誰でも記録しうるが、現場の情報を見てよいかは別の判断になる。

#### 6.10.2 専用の生成もパネルも持たない（実装時の決定）

当初は申し送り専用の生成（`generateArrival`）と専用パネルを持っていた。
これは削除した。**サマリー（→ 6.9）が現場メモを材料に含めた時点で、
同じ注意が2箇所に出る**ようになったため。

いま `arrival.ts` に残るのは**材料集めだけ**で、文にするのはサマリー側。
その結果、

- 外部送信の経路が1つになる（確認も1箇所で済む）
- 伏せ字がサマリー側の仕組みに乗る。現場名は `P2`、本文中の氏名も
  登録済みなら `U4` に変わる（専用生成の頃はメモ本文を素通ししていた）
- 一時停止スイッチも確認画面も、そのまま効く

安全の注意が要約から落ちないよう、材料は独立した見出しで渡し、
指示にも「現場の申し送りがあるときは、安全に関わる内容を優先して拾う」
と明記している。

> **商談での見せ方**: QR をかざす → その場で「反射ベスト必須」が出る。
> **紙のバインダーを開かなくても、現場に着いた瞬間に必要な注意だけ届く**
> ことが、動作で伝わる。

## 7. データモデル（最小構成）

```
users                (id, name, nickname, role, created_at,
                      -- name が唯一の表示名。nickname は移行互換用で name と同値
                      -- role に 'terminal'（打刻端末）を含む
                      partner_company_master_id,
                      -- 協力会社の人だけ協力会社マスタを参照する
                      partner_worker_type,
                      -- 'employee' 固定。社員／パートの区別は廃止（判定は role で行う）
                      status,                 -- 'active' | 'suspended'（'retired' は今後検討）
                      status_changed_at, status_changed_by)
partner_companies    (id, name, short_name, code, status, address, phone, email,
                      -- status は会社ごとの停止。所属者全員のアクセスが一度に切れる
                      -- short_name は名簿の見出し（10文字以内）
                      -- code は名前の前に詰める記号（英大文字3字以内）
                      primary_contact_id,     -- 主担当。自社側の窓口社員
                      counterpart_contact,    -- 副担当。先方の担当者名
                      contract_notes, payment_terms, created_at)
credentials          (id, user_id, credential_id, public_key, sign_count,
                      backup_eligible, backup_state,
                      aaguid, provider_name,      -- 登録時にしか取得できない
                      created_at, last_used_at)
sessions             (id, user_id, credential_id, auth_time,
                      last_active_at, user_agent, ip, region,   -- 記録用。判断には使わない
                      idle_expires_at, absolute_expires_at,
                      revoked_at, revoked_reason, created_at)
invites              (id, code_hash, name, role, expires_at, used_at, created_by, attempt_count,
                      partner_company_id, partner_worker_type,
                      company_name, company_short_name)
                      -- 管理者が名前を付与して対面で渡す。有効期限10分

messages             (id, author_id, body, scope, created_at,
                      withdrawn_at, withdrawn_by,
                      related_type, related_id,   -- internal / sales / place / collection
                      answer_options)             -- related_type='place' が現場れんらく（→ 6.7.1）
message_targets      (message_id, target_type, target_id)
message_reads        (message_id, user_id, read_at)
message_mentions     (message_id, user_id)   -- 回答必須の指名
message_responses    (message_id, user_id, answer, response_text, responded_at)
message_change_history (id, message_id, changed_by, changes_json, changed_at)
attachments          (id, message_id, blob, mime, bytes, created_at)   -- 1MB上限

tasks                (id, title, body, status, due_at, created_by, created_at,
                      place_id,
```

### 7.1 監査ログの範囲 — 全件は記録しない

**サンプルでは監査を最小限にする。** 当初は全ページ閲覧を記録する設計だったが、**一覧の60秒部分更新（→ 3章）が放置タブから記録を生成し続ける**ため成立しない。D1 の書き込み枠にも効く。

「誰がいつ何を見たか」を全件残すのをやめ、**機密が実際に出た瞬間と、状態が変わった瞬間だけ**を `audit_logs`（D1 のテーブル）に記録する。基盤側のログ機構には依存しない。

| 対象 | 記録 | 理由 |
|---|---|---|
| ログイン・ログアウト | **する** | セキュリティの証跡 |
| 停止 / 稼働の切替 | **する** | 誰が誰を、いつ |
| 停止中のログイン試行 | **する** | 「まだアクセスを試みている」が見える |
| パスキーの登録・削除 | **する** | 資格情報の変更 |
| 打刻・打刻修正 | **する** | 労務記録。修正は元の値も残す |
| 添付ファイルの閲覧 | **する** | 個人情報が出る唯一の経路 |
| れんらくの既読 | `message_reads` に記録 | 機能そのもの。監査ログとは別テーブル |
| **一覧の60秒部分更新** | **しない** | 放置タブが記録を生成し続けるため |
| 通常の画面遷移 | **しない** | 量に見合う価値がない |

閲覧を全件残さないぶん、証跡としての網羅性は下がる。実運用で「誰がいつ何を見たか」が要件になった場合も、**ログ基盤ではなく DB のテーブルに記録する**方針は変えず、対象を広げることで対応する。

### 9.2 デモ用のロール切替（実装時の決定）

台本の場面2で数秒で切り替えるため `/demo` を用意した。
**BYOD自体をデモ環境とし、実データは扱わない前提で切替条件を固定してある。**

1. ヘッダーの名前から、現在表示中の本人と打刻端末を除く稼働中利用者へ切り替えられる
2. 切替後は元の利用者が候補へ現れるため、同じ一覧から戻れる
3. 発行するセッションは `credential_id = null`。
   **パスキー検証を経ていないので機密操作は通らない**
4. 誰が誰に化けたかを監査ログに残す（`demo_switch`）

表示中の本人は一覧から除外し、それ以外を役割別に横並びで表示する。プルダウン最上部には「名前切り替えはデモ限定機能です。本番には存在しません」と明記する。

> **実装時に見つけた既存の不具合**: `needsStepUp()` は `auth_time` だけを
> 見ていたため、**パスキーを一度も使っていないセッションでも、
> 発行直後なら機密操作が通ってしまった**。ロール切替を作って初めて
> 露出した。`credential_id` が null なら常に再認証を要求するよう修正した。
> 「直前5分以内の生体認証」を時刻だけで判定してはいけない。

### 9.3 デモデータの作り込み

`/demo` から19名分を投入する。**対比が弱くならないように配る。**

- 「【社員のみ】第二種電気工事士・消防設備士の資格取得補助」を入れ、**協力会社には存在すら見えない**状態を作る。
  これが場面2の主張そのもの（グレー表示でも権限エラーでもなく、無い）
- 「青葉食品工場の全館停電」を管理者を含む参加者へ送り、自社技術者と協力会社を指名して**必須回答1/2**の状態にする
- 協力会社には「さくらクリニック ドレン配管の是正」を1件だけ割り当てる。**0件だと画面が空**で対比が弱い
- 期限切れ・進行中・完了を混ぜ、期限超過の強調が見える状態にする

#### 9.3.1 日付変更時の日次進行

日本時間0時にCron Triggerを実行し、止まったサンプルではなく日々の仕事が動くデモにする

- れんらく2件、やること2件、営業・現場・集金を各1件追加する
- 既存の未完了デモデータから、やること2件と営業・現場・集金を各1件進める
- 営業は引き合い→商談→見積→受注、現場は準備中→施工中→完了、集金は売掛→請求→入金の順に進める
- 問題発生中の業務は自動で進めず、人が状況を確認する運用を保つ
- 日付ごとの実行記録をD1へ保存し、Cronの再実行でも同じ日のデータを二重作成しない
- 追加と進捗変更と実行記録を1つのD1バッチで処理し、途中失敗時は全体を戻す

##### 9.3.2 放置されたものは消す（実装時の決定）

作るだけだと**未読と期限切れが延々と積み上がる**。毎日れんらく2件・
やること2件が増えるので、誰も触らないまま1か月経つと
「現実の会社では起きない量」になり、画面の説得力が落ちる。

日次の掃除（`cleanup`）で2日を過ぎたものを消す。

| 対象 | 条件 |
|---|---|
| やること | 期限を2日過ぎてなお未完了 |
| れんらく | 発信から2日経ってなお**誰も読んでいない** |

れんらくに期限は無いので発信日で見る。**1人でも読んだものは残す** —
読まれた連絡は仕事が動いた証跡で、消すと流れが追えなくなる。

> **本番向けの処理ではない。** 実運用で期限切れを勝手に消したら、
> 未対応や未払いが画面から消える。日次生成が積み続けるぶんを
> 釣り合わせるための、デモ環境限定の仕掛け。

**削除対象は一時テーブルへ固定してから消す。** サブクエリを各 delete に
書くと、`message_reads` を消した時点で「未読のもの」の判定が変わり、
**残すはずだった既読の連絡まで対象になる**。
条件が自分の削除対象テーブルを見ているため、順序に依存してしまう。

ID を集めて IN 句に並べる書き方も採らない。件数が増えると
SQLite の変数上限（999）に当たる。

##### 9.3.3 れんらく・やることは営業／現場へ紐づける（実装時の決定）

**本文に現場名や取引先名が出るなら、その現場・案件へ紐づける。**
同じ日に作る営業・現場・集金があるので、社内扱いのまま置かない。

| 生成物 | 本文 | 紐づけ先 |
|---|---|---|
| れんらく1 | 「現地確認は9時開始です」 | **現場** |
| れんらく2 | 「案件資料が届きました」 | **営業** |
| やること1 | 「既設冷凍庫の電源容量を確認」 | 現場 |
| やること2 | 「提出書類の確認（見積書・注文書）」 | **営業** |

当初はやること1だけが現場に紐づき、残る3件が社内扱いだった。
これだと、

- 現場詳細・営業詳細を開いても、その案件のれんらくが出てこない
- 一覧では本文だけが並び、**どの案件の話か文脈が失われる**
- AIサポートの関連先（→ 6.9）が付かず、`（P2）` で繋がらない

集金には紐づけていない。日次生成の集金は「完了分」として作るもので、
初日に届くれんらくや当日中のやることが指す対象にならないため。
**紐づけ先が無い場合に無理に付けると、かえって嘘の文脈になる。**
- `/demo` の初期化では日次追加分と実行記録も消し、同じ初期状態へ戻す

Cron式はUTCの `0 15 * * *` とし、日本時間の毎日0時に合わせる

### 10.1 機能を足したら、必ず同じ回でデモデータも足す

**新機能は `/demo/seed` にサンプルを追加するところまでで1回分とする。**
データが無い画面は、実装が終わっていても**デモでは存在しないのと同じ**で、
台本（→ 9章）に載せられない。

5.1 の実装時に、既存の seed が**今朝の出勤しか作っていない**ことに
気づいた。集計（→ 6.4）は打刻の上に載るだけの機能なので、
過去の実績が無いと画面が空になり、作ったことを見せられない。

サンプルデータは「動くこと」ではなく**「台本で見せたい状態」**を作る。

| 作る状態 | 狙い |
|---|---|
| 1人だけ時間外が45時間超 | 警告が出る。**全員が超えていると警告の意味が消える** |
| 1人に夜勤（22:00→翌5:00） | 日をまたぐ勤務が出勤日側に乗ることを見せる |
| 1人に退勤の打刻漏れ | 補完せず異常として浮くことを見せる |
| 残りは時間外ゼロの通常勤務 | 上の3つを**例外として際立たせる** |

> **実装時に踏んだ落とし穴**: 既定を 8:00→17:00 にしたところ、
> 休憩を自動控除しない（→ 6.4）ため9時間勤務となり、
> 全員が毎日1時間の時間外を積み上げて**7人中5人に警告が出た**。
> 「1人だけ多い」という台本が成立しない。既定は 8:00→16:00
> （8時間ちょうど＝時間外0）に置く。
>
> 残業役も当初 13時間勤務にしていたが、月110時間は**数字が極端すぎて
> 作り物に見える**。月49時間程度に収め、
> 「よくある忙しい月」に見える範囲にした。

行数は無料枠の書き込みにも効くため、**集計画面で意味を持つ人数に絞る**
（5.1 では7名 × 過去30日）。19名全員に1か月ぶん入れる必要はない。

**Phase 5 系は労務3点（5.1 / 5.2）を先に置く。** 法令義務が絡み、
「あると助かる」ではなく「無いと困る」機能なので、デモの説得力の
伸びが最も大きい（→ 6.4 / 6.5）。5.5（文書）は実装が最も軽いが、
**軽い順ではなく効く順**に並べてある。

いずれも既存の Phase 1〜4 の上に載るだけで、認証・セッション・
稼働停止・監査ログの仕組みは何も変えない。**新しい横断的な仕掛けを
一切導入しないこと**を各機能の設計制約にしてある（→ 6.4〜6.8）。

Phase 1 が最も重く、かつ最もデモ価値が高い。ここを実機で通せた時点で提案の骨格は成立する。

> **添付画像は Phase 2 では実装せず、Phase 5 に送った。**
> 台本（→ 9章）の場面1に添付が登場せず、既読管理だけで山場が成立するため。
> BLOB とワンタイムトークンと監査ログが絡んで Phase 2 で最も重い部分になるので、
> 台本を先に通せる状態にすることを優先した。

## 11. ネイティブアプリの拡張点（Phase 6 以降）

今回は実装しないが、後から差し込めるよう穴を空けておく。

- **WKWebView / Android WebView** で同じ SSR を表示。画面を二重に作らない
- **ブリッジ**: カメラ（レシート撮影）、QR スキャン、プッシュ通知、生体認証
- **セッション橋渡し**: アプリ起動時に `ASWebAuthenticationSession` でパスキー認証 → 得た短命セッション Cookie を WebView に注入。長期トークンは Keychain（Secure Enclave）/ Keystore（StrongBox）に保持し、**WebView 側には一切渡さない**
- SSR 側は `User-Agent` にアプリ識別子を付与して、アプリ経由のときだけカメラ導線を出す

### 11.1 なぜ全社員向けのネイティブアプリを採らないか

**決定: 私物端末（BYOD）はブラウザのままとする。ネイティブアプリは「会社所有の共用打刻端末」に限って将来検討する。**

「VPS + Go をやめた」判断（→ 0章）と同じく、選ばなかった理由を残す。WebView で同じ SSR を包むだけなら実装コストは小さく、一見すると得るものが多いように見えるため、繰り返し議題に上がる。

#### 11.1.1 得られるもの

| 得られるもの | 現状の該当箇所 | 補足 |
|---|---|---|
| パスキー体験の安定 | 3章（プロバイダ差・hybrid の揺れ） | Associated Domains / `assetlinks.json` で RP ID を紐づけ、ブラウザ差の一部を回避できる |
| プッシュ通知 | 6.1「通知はサンプルの対象外」 | 回答必須のれんらく・やることの期限督促に効く |
| 位置情報の常時許可 | 6.3「現在地から場所を選ぶ」 | 毎回のパーミッションダイアログが消える |
| インストールの確実性 | 5章「ホーム画面へ追加する」 | A2HS は iOS で手順が煩雑・削除も容易 |
| 端末の識別 | 3章「認証の対象は人。端末は識別しない」 | Keychain / Keystore に端末鍵を置けば端末束縛が技術的に可能になる |
| オフライン打刻 | 6.3「オフライン対応は行わない」 | 電波の無い現場でのキューイング |
| スクリーンショット抑止 | 4章「防げないこと」 | Android の `FLAG_SECURE` のみ。**iOS では不可** |

#### 11.1.2 それでも採らない理由

1. **コンセプトが崩れる（最大の理由）。** 「端末に何も残さない」の説得力は、*インストール物が無い* ことに強く依存している。BYOD の心理的抵抗はまさに「会社のアプリが自分のスマホに入る」ことであって、WebView の中身がステートレスであるという説明は一段難しい。**訴求の核を、実装上の利便と引き換えに手放すことになる。**

2. **配布がターゲットに合わない。** Apple の審査は社内業務アプリ（一般ユーザーが使えないもの）に厳しく、WebView のラッパーは Guideline 4.2 / 2.1 で落ちやすい。回避策は Apple Business Manager のカスタム App 配布か Enterprise Program（年 $299・法人要件あり）だが、**MDM も ABM アカウントも持たない中小企業・個人商店に、この運用は乗らない。**

3. **保守がゼロでなくなる。** 現状は `npm run deploy` で終わる（→ 0章「保守がゼロになる」）。ここに iOS / Android の2バイナリが加わると、OS 更新追従・証明書更新・ストア審査待ちが恒常コストになる。デモとしても、`wrangler.jsonc` 2枚を並べる説明の切れ味が鈍る。

4. **「即時停止」と衝突する。** 3章の停止設計（→「表示中の画面を落とす」）は、サーバがレスポンスを握っている前提で成立している。オフライン対応やローカル保持を入れた瞬間、**停止済みユーザーの端末にデータが残る窓が開く**。上表の「オフライン打刻」と真っ向から矛盾するため、両取りはできない。

5. **端末に残るリスクがむしろ増える。** WebView は独自のキャッシュ・Cookie・LocalStorage 領域を持つ。4章の `no-store` 設計をアプリ側でも正しく再現する必要があり、実装漏れが「残らないはずのものが残る」事故に直結する。

6. **私物端末への介入という別問題を呼ぶ。** 位置情報の常時取得・端末識別・プッシュ許可は、BYOD では労務／プライバシーの論点になる（→ 12.2-7 協力会社の扱い）。「業務時間外も居場所が取れる仕組みが私物に入っている」は導入時の反対理由として現実に出る。

#### 11.1.3 代わりに採る道

- **打刻専用の共用端末だけは別枠。** 1章の「打刻端末＝仮想ユーザ」は**会社所有**であり BYOD の制約を受けない。キオスク化・オフラインキューイング・端末束縛がすべて素直に嵌まる。「私物はブラウザ、会社支給の打刻端末のみネイティブ」なら、上記1・2・6を回避したまま実利だけ取れる。
- **通知が要るなら Web Push を先に評価する。** iOS 16.4+ は A2HS 済み PWA で Web Push に対応しており（→ 0章の下限 iOS 16+ とは要整合、**16.4 未満は非対応**）、ネイティブ化より遥かに安い。6.1 の通知を解禁する際は、まずこちらを検討する。
- **立替金・出張旅費精算**（→ 0章の保留機能）は、カメラ連携が主題であるため**ネイティブの必要性を示す題材**として残す。これは「アプリが要る場面もある」ことを商談で説明するための材料であって、全社員へのアプリ配布を意味しない。

> 上表の「得られるもの」のうち、4・5・6（インストール確実性／端末識別／オフライン）は共用打刻端末側でほぼ回収できる。**私物端末に対して固有に残るメリットはプッシュ通知とパスキー体験の2点**で、前者は Web Push、後者は 3章の入力吸収でそれぞれ緩和済み。

## 12. 未決の論点

### 12.1 実導入時の構成（最重要）

デモは Cloudflare で作るが、**顧客への実導入では構成を選び直す**。理由は所在地。

- D1 の location hint は `apac` 止まりで、**日本国内を保証しない**
- Cloudflare は米国企業のため、**個情法28条（外国にある第三者への提供）**の対象。SCC/DPA で実務は回るが、本人への情報提供義務が生じる
- 顧問社労士が同席する商談では「データはどこに？」に「東京です」と即答できるほうが強い

想定される導入時の選択肢:

| 構成 | データ所在地 | 保守 | 月額目安 |
|---|---|---|---|
| Cloudflare 継続 | APAC（国内保証なし） | ほぼゼロ | 0〜750円 |
| 東京VPS + Cloudflare 無料プラン前段 | 東京 | OS/TLS/Docker 更新が必要 | 2,000円 |
| Cloud Run 東京 + Neon | 東京（要確認） | OS 更新は不要 | 要試算 |

### 12.1.1 DB の方針 — デモは D1、実運用は Neon を検討

**決定: サンプルは D1 で作る。実運用では Neon（PostgreSQL）を第一候補として検討する。**

#### 12.1.1.1 なぜデモは D1 なのか

**分離のデモが D1 でしか成立しないため。** 本設計の目玉は「SSR Worker に D1 バインディングを書かない＝参照する手段がコード内に存在しない」ことで、これは設定ファイル2枚を並べるだけで説明が終わる（→ 2章）。

Neon は接続文字列で繋がる外部サービスなので、同じことをやっても「SSR には接続文字列を渡していない」という**秘密情報の管理の話**にしかならない。「ハンドルが存在しない」より明確に弱い主張になり、商談での見せ方が崩れる。

副次的な理由:

- Worker から D1 はバインディング経由の内部呼び出しで、**接続確立という概念がない**。Neon は HTTP サブリクエストを消費し、レイテンシも乗る
- D1 の無料枠は**行数**課金で 19 名なら誤差。Neon の無料枠は**コンピュート時間**ベースで、定期的なポーリングを持つ本設計とは相性が良くない

#### 12.1.1.2 なぜ実運用は Neon なのか

**PostgreSQL であることが、そのまま移行先の自由度になる。**

- 上表の「東京VPS」「Cloud Run 東京」いずれに移っても、**DB は Postgres のまま**。D1（SQLite）から移す場合に必要な型・SQL方言・スキーマの書き直しが発生しない
- SQLite は動的型付けで `TIMESTAMPTZ` / `JSONB` / `ENUM` / 配列を持たない。`users.status` の `'active' | 'suspended'` も SQLite では単なる TEXT だが、Postgres なら制約で縛れる
- ブランチ機能で本番/検証のデータを分離できる

#### 12.1.1.3 そのために今やっておくこと

デモと実運用で DB を替える前提なので、**移植の境界を最初から厳格に守る**。

- **D1 へのアクセスは `api/src/store/` の外に出さない。** ハンドラや認可ロジックが SQL を直接書かない
- **SQLite 固有の書き方を避ける** — `INSERT OR REPLACE`、暗黙の型変換、`rowid` 依存など。Postgres に無い、あるいは意味が変わるものは使わない
- **日時は ISO8601 の文字列で統一**して保存する。SQLite に日時型が無いため、ここを曖昧にすると移行時に最も苦しむ
- スキーマは `api/migrations/` に素の SQL で置き、**ORM の抽象に頼らない**（乗り換え時に ORM ごと捨てる羽目になるのを避ける）

> Neon の東京リージョンの有無、Cloud Run との組み合わせの費用は**未確認**。実導入の検討に入る段階で裏を取ること。

### 12.1.2 時刻の持ち方 — 絶対時刻は UTC、カレンダー日付は日本時間

**方針: 保存は UTC のまま変えない。日付境界の計算は `store/japan-time.ts` に集約する。**

このアプリは日本専用だが、**保存値まで日本時間にはしない**。

- **絶対時刻**（`*_at`）… 打刻・発信・更新のように「宇宙のある一瞬」を指すもの。
  `nowIso()` が **UTC** で保存する。海外拠点からの打刻、他システムとの連携、
  Workers のログとの突合を考えると、絶対時刻に地域の文脈を混ぜてはいけない
- **カレンダー日付**（`due_at` / `*_date`）… 「8月15日中」のような**約束事**。
  絶対時刻ではないので、**日本時間の日付文字列**のまま持つ。変換しない

両者は見た目が同じ文字列なので、扱う前にどちらかを確かめる。

**日本の業務日で絞るときは必ず `utcRangeOfJapanDay()` を通す。**
UTC の日付をそのまま使うと、**日本時間の朝9時までが前日**になる。

> **実際に起きた事故**: `nextPunchKind()` だけが `occurred_at` の先頭10文字を
> 日付として使っていた。JST 8時の入場が前日扱いになり、当日の退場から見えず、
> **退場を押しても入場がもう1件記録される**（1回目が失敗して2回目に退場できる）。
> 同じことをする実装が4か所に散らばっていたのが原因なので、
> `japan-time.ts` へ集約し、各所はそれを使う。5つ目を書かせない。

### 12.1.3 可用性とバックアップ

**方針: Cloudflare と Neon に備わる冗長性で十分とし、追加の冗長化は行わない。バックアップは Neon の日次フルエクスポートを別サーバ／NAS に保存する。**

#### 12.1.3.1 冗長化は不要

- **Worker は多重化する対象がない。** 特定のマシンで動くプロセスではなく、リクエストが届いたエッジ拠点で isolate として起動する。「サーバが1台落ちたら止まる」という概念自体が存在しない
- **Neon はストレージ層が標準で冗長化されている。** コンピュートとストレージが分離され、データは複数ノードに複製されたうえでオブジェクトストレージに永続化される
- **書き込みの単一障害点は D1 でも Neon でも解消しない**（プライマリのコンピュートは1つ）。ここは受け入れる

読み取りレプリカは、50人規模では読み取りが軽く**費用対効果が薄い**ため採用しない（コンピュート時間が増えるだけ）。

#### 12.1.3.2 冗長化とバックアップは別物

**ストレージ冗長化は論理的な破壊を防がない。** 誤削除も改ざんも暗号化も、そのまま複製先に伝播する。切り分けは以下のとおり。

| リスク | 対策 | 判断 |
|---|---|---|
| ディスク障害 | 標準の冗長化 | **不要**（自動） |
| ランサムウェア | — | **実質不要**。冗長化があるからではなく、**暗号化対象の OS もファイルシステムも存在しない**ため。SSH で入れるサーバがない |
| 誤削除・誤操作 | PITR | **これで足りる**。スナップショットより上位互換 |
| 不正アクセス | 監査ログ＋ステップアップ認証 | 設計済み（→ 3章） |
| Neon 自体の事故 | **日次フルエクスポート** | **唯一「足す価値がある」もの** |

現実的な脅威はランサムではなく「**認証情報が漏れて正規の経路でデータを操作される**」であり、それは不正アクセスの対策で扱う。

#### 12.1.3.3 日次フルエクスポート

**差分は取らない。** `pg_dump` は本来フルダンプしか取れず、差分をやるなら WAL アーカイブか論理レプリケーションになるが、この規模では不要。

- 50人・1年運用でも**添付を除けば数百MB**（監査ログ約50万行が最大）。`pg_dump -Fc` で日次数十MB に収まる
- **復元手順が単純であることのほうが、この規模では価値が高い。** 差分の復元は「フル＋差分を順に適用」になり、いざという時に手順を誤る
- アプリ層での増分エクスポート（`created_at` で絞る）は、**UPDATE と DELETE を拾えない**ため採用不可。打刻修正や稼働/停止の切替が UPDATE であるため正しく再現できない
- 添付は実運用ではオブジェクトストレージへ移し、そちら側で世代管理する

将来ダンプが GB 級になった場合も、差分を実装するより**論理レプリケーションを常時流すほうが素直**（自前実装が不要で、PITR 相当の粒度が同時に手に入る）。

#### 12.1.3.4 エクスポート先の保護 — 要検討

> **未決。** ダンプには**全従業員の個人情報が平文で入る**。ここまでの設計は「端末に何も残さない」「機密は API Worker だけが触れる」で一貫していたが、NAS に置いた瞬間、**最も無防備な場所に全データの完全なコピーが生まれる**。中小企業の NAS は社内 LAN で共有され、誰でも読める設定になっていることが珍しくない。
>
> 最低限、次の2点を決める必要がある。
> - **ダンプを公開鍵暗号（`age` / `gpg`）で暗号化してから転送し、復号鍵を NAS 側に置かない**
> - **接続情報の置き場所** — NAS 側に Neon の接続文字列を置く構成になりがちで、それも同じ問題を抱える。Neon から push するのか NAS から pull するのかで変わる
>
> ここを外すと、攻撃面が無いという理由で不要と判断したリスクを、**バックアップ経路から呼び戻す**ことになる。

### 12.1.4 課金試算（50人・各自1端末・月額）

**前提**: 稼働22日/月、1人あたり平均**70リクエスト/日**（QR表示30・一覧の60秒部分更新30・画面遷移その他）、書き込み約60行/人日。Neon は最小コンピュート 0.25 CU を想定。

> 専用ハートビートを廃し、一覧の部分更新に統合した（→ 3章）ことで、当初見積もりの 100 リクエスト/人日から約3割減っている。

| | Cloudflare | Neon | 合計/月 |
|---|---|---|---|
| **最小**（利用が朝夕に集中、DB起動 日3h） | $0 | $0（無料枠内） | **$0** |
| **中間**（DB起動 日6h） | $0〜5 | $0〜4 | **$0〜9**（約0〜1,400円） |
| **最大**（DB起動 日11h＋ストレージ増） | $5 | $7 | **$12**（約1,800円） |

**Cloudflare 側はこの規模でも無料枠に収まる。** 月約7.7万リクエスト（日約3,500）に対して無料枠は10万/日、D1 書込は月6.6万行に対して10万行/日。日次上限に一切当たらない。

**変動要因は Neon のコンピュート時間のみ。** Neon はリクエスト数ではなく**DBが起動していた時間**で課金される（Launch $0.106/CU-hour、ストレージ $0.35/GB-month）。オートサスペンドは5分無操作で効くが、50人が日中に散発アクセスすると**実質的に営業時間中ずっと起動したまま**になる。ここが上表の幅を生む。

> **移行時の注意**: 一覧の60秒部分更新（→ 3章）は D1 では無害だが、**Neon ではオートサスペンドを妨げる方向に働く**。実運用へ移す際は、更新間隔をさらに延ばす（180秒など）か、放置検知後に停止する制御を強める。停止状態の確認は本質的に DB 参照なので、**頻度を下げるのが最も素直**。

> 上記のリクエスト積み上げは**実測ではなく見積もり**。桁は合っているはずだが、営業資料に載せる数字にするなら実測してから。Neon 無料枠は 100 CU-hour/project・ストレージ 0.5GB のため、**監査ログを1年保持するとストレージ側で無料枠を超える可能性がある**。

### 12.2 その他

1. **同期パスキー（`BE=1`）の扱い** — 既定は「許可＋プロバイダ名を表示」。iOS も Android GPM も platform authenticator は `BE=1` なので、拒否すると物理セキュリティキーしか使えなくなり BYOD が成立しない。**拒否は選択肢にならない**と結論。表示と利用状況の追跡で担保する
2. **導入時の端末チェックリスト** — Android は Chrome 必須・画面ロック必須。これを導入前の案内に落とし込む必要がある。デモでも「対応端末の確認」画面を1枚用意すると、商談で「うちの職人のスマホで使えるの？」に即答できる
3. **監査ログの保持期間** — デモでは 90 日で Cron 削除（無料枠の 5GB に対して十分すぎるが、削除処理があること自体を見せる）。実導入では 1 年＋R2 アーカイブ

8. **「退職」状態の設計** — 今回は `active` / `suspended` の2値のみ実装する。`retired` を足す場合に決めるべき論点:
   - **パスキーを削除するか** — 停止は残す（復帰できる）。退職は削除する想定だが、削除すると誤操作の復旧が招待からのやり直しになる
   - **氏名の扱い** — 過去のれんらく・打刻・監査ログに氏名が残る。表示を「退職者（田中）」に切り替えるのか、匿名化するのか。監査ログの証跡性と個人情報の削除要求は原則として衝突する
   - **打刻履歴の保存期間** — 労働基準法の記録保存義務（賃金台帳等）との整合。ここは社労士の確認が要る領域
   - 停止で当面の運用は回るため、実導入の要件が固まってから決める
9. **D1 にトランザクションが無い**（実装時に必ず効く） — バッチ実行はできるが、**アプリ側で条件分岐を挟むトランザクションは扱えない**。

   - 招待コードの使用済みマーク — 同上
   - 打刻の nonce 消費は INSERT の主キー衝突で判定する設計なので**問題ない**
   - 意識せず素直に書くと「動いているように見えて競合時だけ壊れる」種類の不具合になる。Postgres へ移行すれば解消するため、`store/` 層に閉じ込める方針（→ 12.1.1）とも整合する
